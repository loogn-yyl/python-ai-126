1异步只对一种情况有效：等

先讲一个必须分清的区别，分不清这个，异步就白学。

IO 密集CPU 密集
在干什么等：等网络、等磁盘、等数据库算：循环、加密、图像处理
CPU 在干嘛闲着满载
典型例子requests 抓网页、读大文件、查数据库算斐波那契、压缩图片、跑模型推理
异步有用吗非常有用，能快几十倍几乎没用，一点都快不了

为什么？想象你在烧水。IO 密集就是「等水开」——你可以同时烧三壶，或者趁等的时候去切菜。CPU 密集是「切菜」——你只有两只手，再多的时间管理技巧也没法让切菜变快。

import time


def cooking(name, sec):
    """IO 密集型：大部分时间在等"""
    time.sleep(sec)
    return f"{name} 好了"


def chopping(n):
    """CPU 密集型：大部分时间在算"""
    total = 0
    for i in range(n):
        total += i * i
    return total


t0 = time.perf_counter()
for name, sec in [("水", 0.1), ("饭", 0.1), ("汤", 0.1)]:
    cooking(name, sec)
io_time = time.perf_counter() - t0
print(f"串行烧三样: {io_time:.1f} 秒（CPU 全程在等）")

total = chopping(500_000)
print("算 50 万次平方和:", total)
print("这段时间 CPU 没有一刻空闲")
串行烧三样: 0.3 秒（CPU 全程在等）
算 50 万次平方和: 41666541666750000
这段时间 CPU 没有一刻空闲

烧三样是 0.3 秒，但这 0.3 秒里 CPU 几乎什么都没做——只是每 0.1 秒醒一次。而算 50 万次循环那 0.03 秒，CPU 是真正跑满的。

异步能做的是「在等的时候去干别的」。
烧水的同时切菜——这就是异步。但它没法让切菜本身变快。所以：
· 抓 100 个网页 → 异步，几十倍提升
· 处理 100 张图片 → 异步没用，要么多进程，要么换 C 扩展

顺带说说 GIL

你可能听说过「Python 有 GIL，所以多线程是假的」。这话只对一半。

GIL（全局解释器锁）的意思是：同一时刻只有一个线程在执行 Python 字节码。所以十个线程做纯计算，并不会比一个线程快十倍——它们得排队拿锁。

但关键在后面：线程在等 IO 的时候会主动释放 GIL。所以十个线程同时发网络请求，是真的同时在等，这也正是异步能快的原因。

任务类型用什么为什么
IO 密集、任务多asyncio单线程，开销最小，能开几千个并发
IO 密集、任务少 / 用的是同步库线程池（明天 D019）不用改代码结构，requests 直接能用
CPU 密集多进程（明天 D019）每个进程有自己的解释器和 GIL，真并行
不要用多线程做计算密集型任务。
GIL 会让它们排队，还多了切换开销，结果常常比单线程还慢。这是 D019 要重点讲的东西，今天先记住这个结论。

2协程：一个能「暂停」的函数

普通函数一旦开始就必须跑到 return，中途没法停。协程可以在某个点上暂停，把控制权交出去，等会儿再回来接着跑。

那个「暂停点」就是 await。而 async def 的作用只是「声明这个函数里允许出现 await」。

import asyncio


async def hello():
    return "hi"


c = hello()
print("类型      :", type(c).__name__)
print("是协程吗  :", asyncio.iscoroutine(c))
print("还没执行  :", "hello() 只是造了一个对象，里面的代码一行都没跑")
c.close()

r = asyncio.run(hello())
print("run 之后  :", r)
类型      : coroutine
是协程吗  : True
还没执行  : hello() 只是造了一个对象，里面的代码一行都没跑
run 之后  : hi
hello() 不会执行任何东西。它只是造了一个「协程对象」，相当于把菜谱写好了放在那儿，还没开火。
忘记 await 或 asyncio.run，你会看到这个警告：
import asyncio


async def hello():
    return "hi"


hello()          # 这样写是错的
print("程序跑完了")
程序跑完了
sys:1: RuntimeWarning: coroutine 'hello' was never awaited

注意 RuntimeWarning 是在最后才冒出来的，而且程序正常退出（退出码 0）。这就是它危险的地方：你以为是成功的，其实那个函数从来没跑过。

这和 D012 的生成器是同一个套路。
生成器函数调用后返回生成器对象，不执行函数体；协程函数调用后返回协程对象，也不执行函数体。两者都要「被消费」才真正跑起来——生成器靠 next() / for，协程靠 await / asyncio.run()。
D012 学的「惰性执行」在这里又出现了一次。

3三件套：async def / await / gather

写法作用用错了会怎样
async def f():声明成协程函数普通函数里写 await → SyntaxError
await x在这里暂停，等 x 完成，同时把 CPU 让给别人写成 x 不加 await → 函数没跑，还发警告
asyncio.run(main())启动事件循环，跑完就关一个程序里调两次 → 第二次报错（循环已关闭）
asyncio.gather(a, b, c)三个一起发出去，等全部完成忘了 * 解包一个列表 → TypeError

顺序 await 还是慢的

这是最容易误解的一点：光加 async / await 不会变快。下面这段还是串行：

import asyncio
import time


async def work(name, sec):
    await asyncio.sleep(sec)
    return name


async def seq():
    t0 = time.perf_counter()
    out = []
    out.append(await work("A", 0.3))
    out.append(await work("B", 0.2))
    out.append(await work("C", 0.1))
    print("顺序 await:", out, f"{time.perf_counter() - t0:.1f} 秒")


asyncio.run(seq())
顺序 await: ['A', 'B', 'C'] 0.6 秒

0.6 秒 = 0.3 + 0.2 + 0.1，一点没省。因为每个 await 都在说「我在这儿等着，等它完事我再往下走」——一个等完才轮到下一个。

gather：一起发出去

import asyncio
import time


async def work(name, sec):
    print(f"  开始 {name}")
    await asyncio.sleep(sec)
    print(f"  结束 {name}")
    return name


async def main():
    t0 = time.perf_counter()
    results = await asyncio.gather(
        work("A", 0.3), work("B", 0.2), work("C", 0.1)
    )
    print("结果:", results)
    print(f"耗时 {time.perf_counter() - t0:.1f} 秒")


asyncio.run(main())
  开始 A
  开始 B
  开始 C
  结束 C
  结束 B
  结束 A
结果: ['A', 'B', 'C']
耗时 0.3 秒

三个「开始」连着打印出来，然后才是「结束」。这就是并发的证据——三个任务都启动了，才开始收结果。总耗时 0.3 秒 = 最慢那个的时间，不是三者之和。

而且注意 results 的顺序：是 ['A', 'B', 'C']，按你传入的顺序，不是完成的顺序。虽然 C 先结束，但结果还是排在第三位。这一点很重要——你可以放心用下标对应输入。

顺序 awaitgather
耗时之和（0.6s）最慢那个（0.3s）
适用后一步依赖前一步的结果彼此独立
结果顺序天然有序按传入顺序，不是完成顺序
怎么选？看有没有依赖。
「先登录拿 token，再用 token 拉数据」——必须顺序 await，因为后一步需要前一步的结果。
「抓 100 个互不相干的页面」——gather，这才是异步的用武之地。

4事件循环：那个看不见的调度器

asyncio.run() 启动的东西叫事件循环（event loop）。你可以把它想成一个永不停歇的调度员：

┌─────────────────────────────────────────┐ │ 事件循环（一个人，单线程） │ │ │ │ 1. 看「就绪队列」里有没有任务 → 有就跑 │ │ 2. 跑到 await → 把任务挂起，去干别的 │ │ 3. 看「等待队列」谁的时间到了 → 挪回就绪 │ │ 4. 队列都空了 → 退出 │ └─────────────────────────────────────────┘

关键结论：所有协程都跑在同一个线程上。所以它们之间没有「线程切换」的成本，也没有「数据竞争」的问题——这是异步比多线程轻量的根本原因。

但这也带来一个硬约束：任何一处阻塞，整个程序都停。
单线程意味着没有别人能替你跑。你在某个协程里写了一句 time.sleep(5)，那五秒里全部任务都卡住。这就是下面第一个坑。

5两个必踩的坑

坑一：在协程里用 time.sleep

这是所有人第一次写异步都会犯的错。看起来完全一样，结果差远了：

import asyncio
import time


async def work_blocking(name, sec):
    print(f"  开始 {name}")
    time.sleep(sec)          # 阻塞！整个事件循环停在这儿
    print(f"  结束 {name}")


async def main():
    t0 = time.perf_counter()
    await asyncio.gather(
        work_blocking("A", 0.3),
        work_blocking("B", 0.2),
        work_blocking("C", 0.1),
    )
    print(f"耗时 {time.perf_counter() - t0:.1f} 秒")


asyncio.run(main())
  开始 A
  结束 A
  开始 B
  结束 B
  开始 C
  结束 C
耗时 0.6 秒

用了 gather，结果还是 0.6 秒，而且变成了「开始-结束-开始-结束」。

原因：time.sleep 是真的让整个线程停住，事件循环也被停住了——它没机会去启动 B 和 C。等 A 的 0.3 秒睡完，才轮到 B。

写法行为用在哪
time.sleep(s)阻塞整个线程，事件循环停摆普通同步代码
await asyncio.sleep(s)只挂起当前协程，循环继续跑别人协程里
判断标准很简单：「这个操作会让线程等着吗？」
会 → 不能用，要换成异步版本（asyncio.sleep、aiohttp、asyncpg）。
不会 → 随便用。
一个 time.sleep 就能让你的异步程序退化回串行，而且没有任何报错。

坑二：requests 是同步的

昨天写的 requests.get() 也是阻塞的。你把它放进协程里，一样会把事件循环卡住。

两种解法：

解法写法适合
换异步库aiohttp / httpx.AsyncClient新项目，直接用
塞进线程池loop.run_in_executor(...)已有同步代码，不想重写
import asyncio
import time


def blocking_request(url):
    """假设这是 D017 里那个 requests.get，同步阻塞"""
    time.sleep(0.1)
    return f"{url} 的标题"


async def fetch(url):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(None, blocking_request, url)


async def main():
    urls = [f"https://site{i}.com" for i in range(1, 6)]
    t0 = time.perf_counter()
    results = await asyncio.gather(*(fetch(u) for u in urls))
    print(f"耗时 {time.perf_counter() - t0:.1f} 秒")
    print("第一条:", results[0])


asyncio.run(main())
耗时 0.1 秒
第一条: https://site1.com 的标题

三个细节：

  • run_in_executor(None, 函数, 参数...)——第一个参数传 None 表示用默认线程池。
  • 参数是平铺的，不是传一个元组：run_in_executor(None, f, a, b)，不是 f((a, b))。
  • 返回值要 await——它返回的是一个 Future，不是结果本身。
默认线程池不是无限的。ThreadPoolExecutor 的默认上限是 min(32, os.cpu_count() + 4)，在你机器上大概是十几到二十几。
所以用这种方式，并发度被线程池大小卡住了。真要开几百个并发，还是得用 aiohttp 这类原生异步库。这个数字每台机器不同，别去记具体值。

6实战：同步 vs 异步，差多少

把昨天那个串行抓取改成异步，对比一下。这是今天的产出。

import asyncio
import time


def sync_fetch(url):
    time.sleep(0.1)
    return url


async def async_fetch(url):
    await asyncio.sleep(0.1)
    return url


urls = [f"https://site{i}.com" for i in range(1, 6)]

t0 = time.perf_counter()
sync_results = [sync_fetch(u) for u in urls]
sync_time = time.perf_counter() - t0


async def main():
    t0 = time.perf_counter()
    results = await asyncio.gather(*(async_fetch(u) for u in urls))
    return results, time.perf_counter() - t0


async_results, async_time = asyncio.run(main())

print(f"同步 {len(urls)} 个: {sync_time:.1f} 秒")
print(f"异步 {len(urls)} 个: {async_time:.1f} 秒")
print("结果一致:", sync_results == async_results)
print("异步耗时 ≈ 单次延迟，不随数量增长")
同步 5 个: 0.5 秒
异步 5 个: 0.1 秒
结果一致: True
异步耗时 ≈ 单次延迟，不随数量增长

四行代码里藏着四个知识点

代码要点
async_fetch(u) for u in urls这是生成器表达式，产生的是协程对象，还没跑（D012 的知识）
asyncio.gather(*...)前面那个 * 不能省。gather 收的是「一堆位置参数」，不是一个列表
sync_results == async_results这是最重要的自检：快了，但结果必须一样
:.1f写成 :.2f 你会看到 0.09 / 0.11 这种抖动，那是正常现象，不是 bug
时间数字每次跑都会变一点点。
你跑出 同步 0.5 / 异步 0.1 就对了。如果异步那行显示 0.5 或更高，说明 gather 里混进了 time.sleep——回去看第一个坑。

为什么必须验证「结果一致」

并发程序最可怕的问题不是慢，是「快了，但结果悄悄变了」。异步里最常见的三种错：

  • 结果顺序对不上：用 asyncio.as_completed() 拿结果时，是按完成顺序返回的，跟输入顺序无关
  • 共用了可变对象：几个协程同时往同一个 list 里 append，虽然单线程不会丢数据，但顺序取决于谁先跑完
  • 异常被吞了：gather 默认「一个抛异常就整体抛」，但异常信息里可能看不出是哪个任务的
加一句 assert 或比较，比看时间数字重要得多。
sync_results == async_results 这行在真实项目里应该写成 assert，它保证你优化的是速度，不是语义。

第 3 题 · 顺序 vs 并发

import asyncio
import time


async def work(name, sec):
    await asyncio.sleep(sec)
    return name


async def main():
    t0 = time.perf_counter()
    a = await work("A", 0.3)
    b = await work("B", 0.2)
    c = await work("C", 0.1)
    print(f"顺序 await: {[a, b, c]} {time.perf_counter() - t0:.1f} 秒")

    t0 = time.perf_counter()
    got = await asyncio.gather(work("A", 0.3), work("B", 0.2), work("C", 0.1))
    print(f"gather    : {got} {time.perf_counter() - t0:.1f} 秒")


asyncio.run(main())
顺序 await: ['A', 'B', 'C'] 0.6 秒
gather    : ['A', 'B', 'C'] 0.3 秒

同一份 work()，同一个 asyncio.run，差别只有「怎么等」：顺序 await 是 0.6 秒（三个相加），gather 是 0.3 秒（取最慢那个）。结果列表完全一样，速度差一倍。

如果你自己跑出来两个都是 0.6 秒，检查这三处：
① 是不是写成了 for w in [...]: await w——这跟顺序 await 没区别
② gather 前面漏了 await——那样程序会瞬间跑完，两个数字都接近 0
③ 函数体里用了 time.sleep——见第 5 节第一个坑

第 5 题 · 结果顺序

import asyncio


async def task(name, sec):
    await asyncio.sleep(sec)
    print(f"  完成 {name}")
    return name.upper()


async def main():
    got = await asyncio.gather(
        task("a", 0.3), task("b", 0.2), task("c", 0.1)
    )
    print("gather 给的结果:", got)

    done = []
    for coro in asyncio.as_completed([task("a", 0.3), task("b", 0.2), task("c", 0.1)]):
        done.append(await coro)
    print("as_completed 给的结果:", done)


asyncio.run(main())
  完成 c
  完成 b
  完成 a
gather 给的结果: ['A', 'B', 'C']
  完成 c
  完成 b
  完成 a
as_completed 给的结果: ['C', 'B', 'A']

对比这两行就明白了：gather 按传入顺序给你，as_completed 按完成顺序给你。
要用下标对应输入，就用 gather；要「谁先好先处理谁」，才用 as_completed。后者配 zip(urls, results) 会直接错位。

第 6 题 · return_exceptions

import asyncio


async def ok(name):
    await asyncio.sleep(0.05)
    return name


async def boom():
    await asyncio.sleep(0.05)
    raise ValueError("坏了")


async def main():
    got = await asyncio.gather(ok("a"), boom(), ok("c"), return_exceptions=True)
    print("结果列表:", [type(x).__name__ if isinstance(x, Exception) else x for x in got])
    print("异常本身:", got[1])

    try:
        await asyncio.gather(ok("a"), boom())
    except ValueError as e:
        print("不设标志时:", type(e).__name__, e)


asyncio.run(main())
结果列表: ['a', 'ValueError', 'c']
异常本身: 坏了
不设标志时: ValueError 坏了

return_exceptions=True 会把异常当成「结果」放进列表里，这样其他任务的结果不会丢。
注意 print(got[1]) 打印出来是 坏了，不是 ValueError: 坏了——所以判断时要 isinstance(x, Exception)，不能靠打印看。批量抓取时一定要开这个标志，否则一个站点失败会让整批结果全丢。

第 7 题 · 限流

import asyncio

running = 0
peak = 0


async def work(i, sem):
    global running, peak
    async with sem:
        running += 1
        peak = max(peak, running)
        print(f"  任务 {i} 开始，当前并发 {running}")
        await asyncio.sleep(0.1)
        running -= 1


async def main():
    sem = asyncio.Semaphore(3)
    await asyncio.gather(*(work(i, sem) for i in range(1, 11)))
    print("历史最高并发:", peak)


asyncio.run(main())
  任务 1 开始，当前并发 1
  任务 2 开始，当前并发 2
  任务 3 开始，当前并发 3
  任务 4 开始，当前并发 1
  任务 5 开始，当前并发 2
  任务 6 开始，当前并发 3
  任务 7 开始，当前并发 1
  任务 8 开始，当前并发 2
  任务 9 开始，当前并发 3
  任务 10 开始，当前并发 1
历史最高并发: 3

async with sem 就是「拿不到信号量就在这儿排队」。信号量只有 3 个，所以同时最多 3 个任务在跑。
真实场景必须有这一层：你要抓 1000 个网页，一次全发出去，对方服务器会把你当攻击，你自己的连接也会耗尽。限流不是优化，是必需品。

第 8 题 · 超时

import asyncio


async def slow():
    await asyncio.sleep(2)
    return "终于好了"


async def main():
    try:
        r = await asyncio.wait_for(slow(), timeout=0.5)
        print("拿到:", r)
    except TimeoutError:
        print("超时了，0.5 秒内没完成")

    try:
        r = await asyncio.wait_for(asyncio.sleep(0.01, result="很快"), timeout=0.5)
        print("正常:", r)
    except TimeoutError:
        print("不应该走到这里")


asyncio.run(main())
超时了，0.5 秒内没完成
正常: 很快

asyncio.wait_for 抛的是内置的 TimeoutError（Python 3.11 起它和 asyncio.TimeoutError 是同一个类，写哪个都行）。
和 D017 的 requests 超时是一回事，但表达方式完全不同：requests 是参数，这里是包一层。原理相同——「等不到就别等了」要有明确的期限。

# D018 笔记 · 异步编程

## 一句话
异步解决的是「等」——IO 密集才有用，CPU 密集一点快不了。
烧水可以同时烧三壶（IO），切菜只有两只手（CPU）。

## IO 密集 vs CPU 密集
IO 密集：等网络/磁盘/数据库，CPU 闲着   → asyncio / 线程池
CPU 密集：循环/加密/图像处理，CPU 满载  → 多进程（GIL 挡住多线程）

## GIL
同一时刻只有一个线程执行 Python 字节码
→ 多线程做计算不会变快
→ 但线程等 IO 时会释放 GIL，所以异步才有效

## 协程
async def f()   = 声明（允许里面出现 await）
f()             = 造了一个协程对象，一行都没跑 ★和生成器一样是惰性的
await x         = 暂停在这里，把 CPU 让给别人
asyncio.run(main()) = 启动事件循环，跑完就关（一个程序只调一次）

## 三件套
async def / await / asyncio.gather
★ 光加 async/await 不会变快，顺序 await 还是 0.6 秒
gather(*coros) → 一起发出去，耗时 = 最慢那个
★ gather 结果按「传入顺序」，不是完成顺序
as_completed → 按完成顺序（拿结果时不能再按下标对应输入）

## 事件循环
单线程调度：就绪队列 → 跑 → 遇 await 挂起 → 查等待队列 → 挪回
所有协程同一个线程 → 没有切换成本，也没有数据竞争
但 → 任何一处阻塞，整个程序停

## 两个坑
1 time.sleep(s)     阻塞整个线程，事件循环停摆 → await asyncio.sleep(s)
  症状：用了 gather 还是 0.6 秒，输出变成「开始-结束-开始-结束」，不报错
2 requests 是同步的 一样会卡 → aiohttp / httpx，或 loop.run_in_executor
  run_in_executor(None, f, a, b)  参数平铺，返回值要 await
  默认线程池 min(32, cpu+4)，并发度被它卡住

## Semaphore 限流
async with sem:  ...
Semaphore(3) → 同时最多 3 个
抓 1000 个页面一次全发出去 = 打人家服务器 + 自己连接耗尽
限流不是优化，是必需品

## 超时
await asyncio.wait_for(coro, timeout=0.5) → TimeoutError

## 纪律
- 快了必须验证结果一样：assert sync_results == async_results
- 并发程序的错不是慢，是「快了但结果悄悄变了」
- 计时只记量级，:.2f 会抖动，别当 bug
