2自测二十题：先答，再点开

十道命令、十道概念。答案里的命令都能现场验证，别只看。

命令十题

1. ls -a 和 ls -A 差什么？

-a 连 . 和 .. 都列出来，-A 列出其他隐藏文件但不含这两个。想看「这目录里到底有什么」用 -A，两个点占两行纯属噪音。

2. wc -l 数出来的行数为什么可能比实际少一行？

因为它数的是换行符个数。文件最后一行没有换行符时，那一行不算。11-22 修作品集时 sample_access.log 就栽在这上面：wc -l 显示 8、程序读到 9。
补换行：printf '\n' >> 文件。

3. du -sh * 和 df -h 分别回答什么问题？

du 回答「这些东西各占多少」（按目录统计）；df 回答「磁盘还剩多少」（按文件系统统计）。
「磁盘满了但 du 加起来对不上」的经典原因是「已删除但还被进程占用的文件」——df 算它，du 看不到。用 lsof +L1 找。

4. grep -v "200" 是干什么的？

反选：输出不含 200 的行。排错时最省事的一招——「除了正常请求，还剩什么」一行就出来了，不用写匹配 4xx/5xx 的正则。

5. find . -name *.py 不加引号会怎样？

shell 会先在当前目录把 *.py 展开成实际文件名，于是 find 只去找那几个名字，子目录里的全漏了。当前目录没有 .py 时，bash 会把字面量传过去（碰巧能用），zsh 会直接报 no matches found 不执行。
规则：-name 后面的模式一律加引号。

6. 为什么 ssh 私钥必须 chmod 600？

权限太宽时 ssh 会认为这把钥匙可能被别人动过，直接拒绝使用，而且只在 ssh -v 里给一行 UNPROTECTED PRIVATE KEY FILE，正常使用时毫无提示。
四个数记牢：.ssh 700、私钥 600、公钥 644、config 600。

7. > f 2>&1 和 2>&1 > f 差在哪？

&1 复制的是「此刻 stdout 指向哪里」。前者：stdout 先进文件，stderr 跟着进文件，两个都进文件；后者：stderr 先跟着「屏幕」，stdout 再进文件，报错留在屏幕上、文件里只有正常输出。
从左往右读，就不会记反。

8. tar -xzf a.tar.gz -C /tmp/x 里 -C 干什么？

先切到 /tmp/x 再解压，解出来的东西落在那个目录里，不污染当前目录。解别人的包之前，先用 tar -tzf 看一眼内容——包里可能有 ../../ 这种往外写的路径。

9. vim 里 :%s/8080/8000/g 的 % 和 g 分别管什么？

% = 整个文件（不加就只改光标那一行）；g = 每行所有匹配（不加只改每行第一个）。
少写 % 是 vim 替换最常见的错：以为全改了，其实只改了一处。

10. ssh -T git@github.com 出现什么算密钥配好了？

看到 Hi 你的用户名! 就成了。中间那行 Offering public key 是它在试哪把钥匙——连不上时看这一行，钥匙不对就是 IdentityFile 配错了。

概念十题

11. 为什么删文件看的是目录的写权限？

因为「删除」改的是目录里的名单，不是文件内容。所以文件设成只读 r--r--r--，只要目录你有 w，照样删得掉；反过来，文件你有 w 但目录没有 w，能改内容、删不掉文件。

12. set -euo pipefail 三个开关各管什么？

-e 命令失败就退出；-u 用未定义变量就报错；-o pipefail 管道里任一命令失败整条算失败。
它管不到的地方：if 条件里的命令、cmd || true、以及 set -e 生效前的部分。

13. 为什么读文件要用 while IFS= read -r line，不用 for line in $(cat f)？

后者会按空格和换行一起切分，一行 6 个词的日志会被拆成 6 次循环；而且管道版会让循环在子 shell 里跑，循环里的变量外面读不到（计数永远是 0）。
正确写法：while IFS= read -r line; do ...; done < 文件。

14. "$@" 和 $* 有什么不同？

"$@" 把每个参数各自作为独立的一项传下去；$* 把它们拼成一个字符串。转发参数永远写 "$@"——这是唯一能保持参数个数和内容的写法。

15. Git 的三个区分别是什么，各由哪条命令推动？

工作区 →（git add）→ 暂存区 →（git commit）→ 本地仓库 →（git push）→ 远端。
暂存区的存在意义是「挑着提交」：同时改了三件事，可以分三次提交。

16. git add 之后 git diff 变空，改动丢了吗？

没丢。只是「工作区 vs 暂存区」现在一样了，所以没差异。用 git diff --cached 看「暂存区 vs 最新提交」，改动都在那儿。commit 之前跑一次 --cached 是能省很多麻烦的习惯。

17. 为什么加了 .gitignore，文件还在被提交？

因为忽略规则只对「未跟踪的文件」生效，已跟踪的管不着。双保险：改规则 + git rm --cached 文件（只从索引移除，本地文件留着）。
验证用 git check-ignore -v 文件，它会告诉你命中了哪一行规则；对已跟踪文件它没有输出，这本身就是诊断信息。

18. reset 的 --soft / --mixed / --hard 各动什么？

--soft 只退指针，改动留在暂存区；--mixed（默认）退指针 + 重置暂存区，改动退回工作区；--hard 连工作区一起丢。
--hard 前先 git stash：不确定要不要丢的东西，收进抽屉比直接删便宜太多。

19. rebase 之后为什么提交号变了？

因为 rebase 不是「移动提交」，是「把你的提交在新的底座上重新提交一遍」——内容一样，但父提交变了，哈希必然变。这也是「不要 rebase 已共享分支」的原因：别人手里的旧提交和你的是两套历史，一推就冲突，只能强推。

20. systemctl enable 和 start 差什么？

enable = 开机自启（写进配置），start = 现在就启动（这一次）。enable --now 才是两个都做。
只 start 不 enable，重启机器之后服务就没了——这是「昨天好好的，今天打不开」最常见的成因。

# 我的 Git 工作流

## 每天的三步
1. 改文件 → git status --short 看改了什么（左暂存右工作区）
2. git add -A → git diff --cached 看这次要提交什么（必看！）
3. git commit -m "写清做了什么" → git pull --rebase → git push

## 我的 gl 做了什么（逐行解释）
git add -A                    # 全部放进暂存区
git diff --cached --quiet     # 没改动就早退（空提交守卫）
git commit -m "${1:-...}"     # 提交，默认信息是日期
git pull --rebase             # 先拉远端，把我的提交接到后面
git push                      # 推上去
# 顺序固定：先 commit 再 rebase 再 push
# 反过来（先 pull 再 commit）会遇到「有未提交改动不能 rebase」

## 看状态
git status --short       左=暂存区 右=工作区
git diff                工作区 vs 暂存区
git diff --cached       暂存区 vs 最新提交
git log --oneline --graph -10
git branch -vv          看跟踪谁、领先落后几条
git log --oneline HEAD..origin/main    落后几条

## 分支
git switch -c feat-x        新建并切
git switch main             切回
git merge feat-x            合并
git branch -d feat-x        删掉（已合并的）

## 冲突
UU 文件 → 手工改（删掉 <<< === >>> 三行）→ git add 文件 → git commit
解不下去：git merge --abort

## 后悔
git restore 文件              丢掉工作区改动（单文件）
git restore --staged 文件     取消 add
git reset --soft HEAD~1      退一条提交，改动留暂存区
git reset --hard HEAD~1      全丢（先 git stash！）
git revert 提交号             已 push 的用这个
git reflog                   删错了来这儿找

## 远端
git remote -v
git push -u origin main      第一次要 -u
git tag -a v1.0 -m "说明"  →  git push origin v1.0   ← 别忘了推
git rebase main             接到最新 main 上（改提交号！）
# 铁律：已 push 的分支不 rebase

## 我踩过的坑
- .gitignore 对已跟踪文件无效 → git rm --cached
- add 之后 git diff 变空是正常的，用 --cached 看
- reset --hard 没有确认框
- 新仓库首次 push 被拒 → 远端建仓时勾了 README，先 pull --rebase
「我的 gl 做了什么」这一节今天必须写。三周来你敲了几十次 gl，但它一直是黑箱——今天之后它应该是一段你能逐行解释的代码。哪天 push 失败、rebase 冲突，你会知道该停下看哪一步，而不是反复重试。

第 4 周结束。三周前你在写 print，两周前在写类，一周前在做命令行工具；现在你能把东西部署到一台机器上、让别人用一个链接打开它。
这是「会写代码」和「能交付」之间的那道坎——今天你跨过去了。
