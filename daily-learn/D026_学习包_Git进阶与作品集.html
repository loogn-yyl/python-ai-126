1remote：本地仓库和远端的对照表

你的本地仓库和 GitHub 上那个仓库，是两个独立的仓库。它们靠 remote（远端地址）和「跟踪分支」建立起对应关系，之后 push/pull 才有方向。

cd ~/python-learn
git remote -v
git branch -vv
origin	git@github.com:loogn-yyl/python-ai-126.git (fetch)
origin	git@github.com:loogn-yyl/python-ai-126.git (push)
* main 8a3f2c1 [origin/main] 学习记录 11-22
东西是什么读法
origin远端地址的别名，不是特殊关键字「origin」只是习惯叫法，你叫它 github 也行
origin/main远端 main 在你本地的快照（只读）不要直接改它，它由 fetch/pull 更新
[origin/main]当前分支跟踪哪个远端分支有了它，git push 不用写参数
第一次 push 时那个 -u，就是建立这个跟踪关系。git push -u origin main = 「推到 origin 的 main，并记住以后默认推这儿」。忘了 -u 也能推上去，但下次 git push 会报「没有上游分支」——不是出错，是它不知道该推哪儿。
# 加一个远端（一个仓库可以有多个）
git remote add github git@github.com:loogn-yyl/xxx.git
git remote -v

# 改地址（仓库改名、从 HTTPS 换 SSH 时用）
git remote set-url origin git@github.com:loogn-yyl/新名字.git
换仓库名或从 HTTPS 换 SSH 时，git remote set-url 是最省事的做法，不要 remote remove 再 add——那会丢掉跟踪关系，得重新 -u。你的仓库走的是 SSH（git@github.com:...），这依赖昨天配的那把密钥，所以 ssh -T git@github.com 能看到 Hi，是一切 push 的前提。

2pull 与 fetch：一个是「拿回来」，一个是「拿回来并合进来」

命令做什么动你的工作区吗
git fetch把远端的新提交下载到 origin/main不动
git pull= fetch + merge会合并，可能产生冲突
git pull --rebase= fetch + rebase会重放你的提交
git fetch
git log --oneline HEAD..origin/main     # 远端有、我没有的提交
git log --oneline origin/main..HEAD     # 我有、远端没有的提交
这两条 .. 命令值得背下来。push 之前跑一遍，就知道「我要推几条上去」「远端有没有我不知道的东西」——比 git status 那句模糊的「ahead 2, behind 1」具体得多。
只在自己一个人用的仓库里，pull 和 pull --rebase 差别不大。但一旦有协作，或者你在两台机器上推同一个仓库（你的情况：Mac 写代码，Windows 可能也 commit），差别就出来了：
pull 会产生「Merge branch 'main' of github.com...」这种没信息量的合并提交；pull --rebase 把你的本地提交接到远端最新提交后面，历史是一条直线。你的 gl 用的就是这个，所以你的历史一直是干净的。

3PR：不是权限流程，是「请别人看一眼」的机制

一个人开发也需要 PR 吗？需要，但目的不是审批，是给自己留一个「这次改动范围是什么」的记录，而且 PR 页面能并排看 diff、逐行评论，比在终端里翻强得多。

① 从 main 开分支 git switch -c feat-login ② 改代码、提交 git add -A; git commit -m "..." ③ 推到远端 git push -u origin feat-login ④ 在 GitHub 上开 PR 网页操作：base=main ← compare=feat-login ⑤ 看 diff、写说明 自己 review 一遍，常常能发现误提交 ⑥ 合并 三种方式，见下表 ⑦ 删掉分支 git switch main; git pull; git branch -d feat-login
合并方式结果什么时候用
Merge commit保留全部分支提交 + 一个合并提交功能分支有多条有意义的提交
Squash and merge把整个 PR 压成一个提交接在 main 上个人项目首选：一个功能一个提交，历史最干净
Rebase and merge把每条提交依次接到 main 上，不产生合并提交想要线性历史又不想丢提交粒度
Squash 的代价：分支上的提交历史没了。如果那个分支里有「先写错再改对」的过程，squash 之后只剩最终结果——对作品集来说是好事，对排查问题来说是坏事。个人项目推荐 squash，因为你的提交信息往往写得随意（「改一下」「再改」），压成一条写清楚反而更好看。

4rebase：把你的提交「重放」到新的起点上

rebase 不是合并，是「撤销我的提交、在新的基础上重新提交一遍」。因为重新提交，所以提交号会变——这一点很重要。

# 实测：main 上有一个 B，feat 从 A 分叉后有两个提交 C、D
git log --oneline --graph --all
* 8c073cc D feat 上
* df472d1 C feat 上
| * 9f8a47c B main 上
|/
* fa3030f A 初始
git rebase main
git log --oneline --graph --all
* 0a3c6b7 D feat 上
* e440d00 C feat 上
* 9f8a47c B main 上
* fa3030f A 初始
对比两张图，只看三件事：
① 分叉消失了，变成一条直线；
② C 和 D 的提交号变了（df472d1 → e440d00，8c073cc → 0a3c6b7）——因为它们被「重新提交」了一遍；
③ A 和 B 的提交号没变——它们不在被重放的范围内。
这就是 rebase 的全部机制：把你的提交摘下来，接到新底座上，一个个重新贴上去。
铁律：不要 rebase 已经共享出去的分支。因为提交号变了，别人手里的旧提交和你的新提交是两套历史，一 push 就会互相打架，然后你只能强推，而强推会把别人的工作覆盖掉。
判断标准：这个分支你 push 过吗？别人可能基于它工作吗？两个都是「是」→ 用 merge；只有你自己的本地分支 → 随便 rebase。

最常用的两个 rebase 场景

# 场景一：本地分支落后了，想接到最新的 main 上
git switch feat-x
git rebase main

# 场景二：整理自己那几个乱七八糟的提交（还没 push）
git rebase -i HEAD~4
# 编辑器里把 pick 改成 squash 就能合并、改成 reword 就能改信息、drop 删掉
git rebase -i 是「提交整理」的唯一工具，但今天不用深究。记住它能做三件事就够：合并几个提交（squash）、改提交信息（reword）、删掉某个提交（drop）。做之前先 git log --oneline -5 记下提交号，搞砸了用 git rebase --abort 或 reflog 回来。
# rebase 卡在冲突里时
git rebase --continue     # 解完一个冲突，继续
git rebase --abort        # 整个放弃，回到 rebase 之前
git rebase --skip         # 跳过这个提交（慎用，等于丢掉它）
rebase 的冲突可能不止一次。因为它逐个重放提交，每个提交都可能冲突——解完一个要 git add 再 --continue，可能重复好几次。这是很多人「rebase 到一半放弃」的原因：以为解完一次就结束了。--abort 随时可以全身而退。

5tag：给「能跑的那个版本」拍个记号

提交号是人类记不住的，tag 是给人看的名字。作品集打一个 v1.0，别人点进去下载的就是那一刻的完整代码。

# 附注标签（推荐）：带作者、日期、说明
git tag -a v1.0 -m "阶段一作品集：四个项目全部可运行"

# 轻量标签：只是一个名字，没有额外信息
git tag v1.0-lw

git tag                      # 列出所有
git show v1.0 | head -n 8    # 看标签信息

# 推到远端（默认不推标签！）
git push origin v1.0
git push origin --tags       # 一次推全部
tag v1.0
Tagger: loogn <你的邮箱>
Date:   ...

阶段一作品集：四个项目全部可运行
git push 不会自动推标签。这是最容易忘的一步——本地 git tag 看得见、GitHub 上没有，然后你发给别人的 tag 链接是 404。打完 tag 一定补一句 git push origin v1.0。
版本号怎么起：v主.次.修订。作品集不需要严格语义化，你知道 v1.0 是「阶段一提交的那一版」就够了。后面 D036 做完数据库项目打 v2.0，形成一条能看出来的成长线——这比任何简历描述都直观。

为什么用 cp -R 源/. 目标/ 而不是 cp -R 源 目标：前者把目录里的内容复制过去，后者会多套一层 portfolio/。那个 /. 是「这个目录里面的所有东西」的意思，复制目录内容时都用这个写法。

给新仓库配一个快捷命令

# 加到 ~/.zshrc，然后 source ~/.zshrc
glp() {
  cd ~/python-portfolio || return 1
  git add -A
  git diff --cached --quiet && { echo "没有改动"; cd - >/dev/null; return 0; }
  git commit -m "${1:-作品集更新 $(date +%m-%d)}"
  git pull --rebase || return 1
  git push
  cd - >/dev/null
}
它和你现有的 gl 结构一样，多了两件事：cd 进去再 cd 回来（所以你在任何目录都能用），以及「没有改动就早退」。git diff --cached --quiet 的退出码是「有没有差异」，用它当空提交守卫比看 git status 的输出可靠。

8练习八道

第 1 题 · 看当前分支跟踪谁、领先落后几条

答案 
cd ~/python-learn
git branch -vv
git fetch
git log --oneline HEAD..origin/main | wc -l    # 落后几条
git log --oneline origin/main..HEAD | wc -l    # 领先几条

branch -vv 里的 [origin/main: ahead 1] 就是答案，但它不会主动去问远端——所以要先 git fetch，否则看到的是上次 fetch 时的旧状态。「明明推上去了，本地还说 ahead」就是没 fetch。

第 2 题 · 建一个本地分支，rebase 到最新 main 上，看提交号变了没

答案 
cd ~/git-lab/demo
git switch -c try-rebase
echo x >> two.txt && git add -A && git commit -m "try: 改 two"
git log --oneline -1                # 记下提交号

git switch main
echo y >> README.md && git add -A && git commit -m "main 前进一条"

git switch try-rebase
git rebase main
git log --oneline -1                # 提交号变了

两次 git log --oneline -1 的提交号不同，这就是 rebase 改写了历史。这也是为什么「已经 push 的分支不能 rebase」——远端还指着旧提交号，你一 push 就会被拒绝，然后只能强推。

第 3 题 · 打一个 tag 并推到远端

答案 
git tag -a v1.0-练习 -m "练习用标签"
git push origin v1.0-练习
git ls-remote --tags origin

git ls-remote --tags origin 是「远端到底有没有这个标签」的唯一可靠验证——本地 git tag 只说明你打了，不说明推上去了。

第 4 题 · 撤销一次已经 push 的提交（用 revert）

答案 
git log --oneline -3
git revert 提交号            # 会打开编辑器让你确认信息
git push

revert 会产生一个新提交，内容是「把那个提交的改动反向应用」。好处是不改写历史，所以不需要强推，也不会影响别人。
注意：revert 一个合并提交要加 -m 1（指定保留哪一边作主线），否则 git 不知道该按哪个父提交算。

第 5 题 · 用 PR 流程合入一个小改动（哪怕只有你自己）

答案 
# 在作品集仓库里
git switch -c docs/better-readme
# 改 README
git add -A && git commit -m "docs: 补运行说明"
git push -u origin docs/better-readme
# 到 GitHub 上开 PR，选 Squash and merge
git switch main

git branch -d docs/better-readme

重点在最后两步：合并之后本地 main 要 pull 一次（squash 之后远端 main 多了一个你本地没有的新提交），然后删掉本地分支。不 pull 就继续改，下次 push 会被拒绝。

# D026 Git 进阶笔记

## 一、push / pull / fetch
fetch 只更新 origin/main，不动工作区
pull = fetch + merge；pull --rebase = fetch + rebase
git log --oneline HEAD..origin/main   落后几条
git log --oneline origin/main..HEAD   领先几条

## 二、rebase 的本质
摘下来 → 接到新底座 → 重新提交 → 提交号变了

今天最容易翻车的一步：新仓库第一次 push 被拒绝。原因通常是远端建仓库时勾了「Add a README」或「.gitignore」。解法：git pull --rebase origin main 再 git push，不要强推——强推会删掉远端那个 README。
