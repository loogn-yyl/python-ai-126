0. 先建立这张图

Git 有四个位置，所有命令都是在它们之间搬东西：

工作区（你编辑的文件）
   ↓ git add
暂存区（staging，即将提交的内容）
   ↓ git commit
本地仓库（.git 里的历史记录）
   ↓ git push
远程仓库（GitHub）

新手 90% 的困惑来自分不清"改动在哪一层"。搞不清的时候永远先跑 git status，它会告诉你每个文件现在处于哪一层、下一步该做什么。

1. 一次性配置（只做一次）

git config --global user.name "loogn-yyl"
git config --global user.email "你的邮箱"
git config --global init.defaultBranch main    # 新仓库默认分支叫 main
git config --global core.quotepath false       # 中文文件名正常显示，不乱码

git config --list                              # 看当前所有配置

配置不对会导致提交记录作者错乱，这步在第一次 commit 前必须做完。改完不用重新登录。

2. 日常三连（每天就这几条）

git status                 # ① 看现在什么状态
git add .                  # ② 把所有改动放进暂存区
git commit -m "D008: 类与对象"   # ③ 提交，写上说明
git push                   # ④ 推到 GitHub

提交信息写什么：一句话说清这次做了什么。D008: 类与对象 比 update、fix、1 有用一万倍——三个月后你只能靠这行字找回当时的思路。

git add day08/exercise.py   # 只加某个文件（推荐，比 git add . 可控）
git add -A                  # 加所有改动，含新建和删除的文件
git commit -am "改个 typo"   # ⚠️ 只对「已跟踪」文件生效，新建的文件不会被提交

-am 那个坑要记牢：新建的文件必须先用 git add 加一次，之后才能靠 -am 省事。

3. 看历史

git log --oneline --graph --all    # ★ 最实用：一行一条，带分支图
git log -p -2                      # 看最近 2 次的详细改动
git show <提交哈希>                 # 看某次提交具体改了什么
git log --oneline -- day08/        # 只看某个目录的历史

建议给 git log 配个别名，省得每次敲一长串：

git config --global alias.lg "log --oneline --graph --all"
# 之后直接 git lg

4. 看差异（提交前先看改了什么）

git diff                  # 工作区 vs 暂存区（还没 add 的改动）
git diff --staged         # 暂存区 vs 最新提交（即将提交的内容）
git diff HEAD             # 工作区 vs 最新提交（全部改动，最常用）
git diff main day08       # 两个分支之间的差异

养成习惯：git add 之后、commit 之前跑一次 git diff --staged，确认没有把 .DS_Store、密码、临时文件混进去。

5. 撤销（最容易搞坏的部分，按场景查）

我的情况命令危险度
改了文件，还没 add，想全部还原git restore 文件名⚠️ 改动直接消失
已经 add 了，想撤出暂存区（保留改动）git restore --staged 文件名安全
刚提交，想改提交信息git commit --amend -m "新信息"安全（未推送时）
刚提交，想撤销但保留改动git reset --soft HEAD~1安全
刚提交，想撤销且丢弃改动git reset --hard HEAD~1🚨 危险，改动全没
已经 push 了，想撤销git revert <哈希>安全，生成一条反向提交

规矩：只有还没 push 的提交才用 reset，已经 push 的一律用 revert。 对已推送的历史用 reset 再强推，会把别人的本地仓库搞乱。

救命命令：reflog

git reset --hard 之后发现删错了，别慌，还有救：

git reflog                  # 列出所有 HEAD 移动记录（包括被 reset 掉的）
git reset --hard <哈希>      # 回到那个状态

reflog 记录本地 90 天内的所有操作，是 Git 的"后悔药"。唯一救不回来的是从没提交过的改动（那些 Git 根本不知道存在）。

6. 分支

git branch                     # 列出本地分支（* 是当前所在）
git switch -c day08-feature    # 新建并切换（现代写法）
git switch main                # 切回 main
git merge day08-feature        # 把该分支合并进当前分支
git branch -d day08-feature    # 删除已合并的分支
git branch -D day08-feature    # 强制删（未合并也能删，慎用）

git switch / git restore 是 Git 2.23 起的新命令，替代了老教程里的 git checkout（一个命令干太多事，容易误操作）。看到老教程写 git checkout 不用慌，功能对应关系是：

老写法新写法干什么
git checkout 分支名git switch 分支名切分支
git checkout -b 新分支git switch -c 新分支建并切
git checkout -- 文件git restore 文件丢弃改动
git reset HEAD 文件git restore --staged 文件撤出暂存区

学习阶段建议：一个人一个仓库，尽量都在 main 上做，需要试验时再开分支。分支管理是团队协作才必需的东西。

7. 远程仓库

git remote -v                          # 看远程地址（应该是 git@github.com:...）
git remote add origin git@github.com:用户/仓库.git
git push -u origin main                # 首次推送并建立跟踪（-u 只需一次）
git push                               # 之后直接 push

git fetch                              # 只下载远程更新，不动你的文件
git pull                               # 下载 + 合并（= fetch + merge）
git pull --rebase                      # 下载 + 变基（历史更干净，冲突时更好处理）

fetch 和 pull 的区别：fetch 是"看看远程有什么变化"，安全；pull 是"拿下来并直接合并进你的文件"，可能产生冲突。不确定的时候先 fetch 再决定。

8. 冲突处理

冲突长这样（Git 在文件里插入了标记）：

<<<<<<< HEAD
你的版本
=======
远程/别人的版本
>>>>>>> origin/main

处理步骤：

  1. 打开文件，手动编辑成最终想要的样子，删掉 <<<<<<<、=======、>>>>>>> 三行标记
  2. git add 冲突文件（告诉 Git 已解决）
  3. git commit（不用加 -m，Git 会生成默认信息）
git merge --abort      # 合并途中反悔，回到合并前
git rebase --abort     # 变基途中反悔
git status             # 忘了处理到哪一步？看它

9. 临时存一下（stash）

写了一半，突然要切分支修别的东西：

git stash              # 把当前改动存起来，工作区变干净
git stash list         # 看存了哪些
git stash pop          # 取回最近一次（并从栈里删掉）
git stash apply        # 取回但保留在栈里（想多次使用）
git stash drop         # 丢掉最近一次

10. 忽略文件（.gitignore）

项目根目录建 .gitignore，写进去的文件 Git 永远不会跟踪：

__pycache__/
*.pyc
.DS_Store
.venv/
*.log
.env

规则要点：

  • __pycache__/ 结尾带斜杠 = 只匹配目录
  • *.pyc = 匹配所有此类文件
  • !important.log = 感叹号表示例外（不忽略）

已经提交过的文件，加进 .gitignore 不会自动消失，要先从索引里移除：

git rm --cached 文件名      # 只从 Git 移除，本地文件保留
git commit -m "移除不该提交的文件"

.DS_Store 是 Mac 特有的坑：访达自动生成的目录属性文件，会出现在每个文件夹里。必须写进 .gitignore，否则每天提交都会带上一堆垃圾。

SSH 是否通的唯一验证命令：

ssh -T git@github.com
# 成功会显示：Hi 用户名! You've successfully authenticated...
# 看到 "does not provide shell access" 是正常的，不用管

12. 你每天的固定流程

cd ~/python-learn
git status                        # 先看有什么改动
git add day08/                    # 加今天的目录
git diff --staged                 # 确认没混进不该提交的东西
git commit -m "D008: 类与对象"
git push

如果之前配了 gl 快捷函数（见 GitHub 指南第 5 节）：

gl                  # 用「学习记录 10-29」作为提交信息
gl "D008: 类与对象"  # 带自定义信息

验收标准：github.com 上能看到今天的提交，且文件内容完整。只 commit 不 push 等于没上传。

13. 六条纪律

  1. 每天 push 一次，别攒一周。 攒着一旦出问题，回滚成本是几何级增长的。
  2. 提交前先 git status。 看清楚要提交什么，比事后回滚省事一百倍。
  3. 提交信息写具体。 D008: 类与对象 好过 update。
  4. 不给 git push 加 --force。 尤其别用 --force 推 main。真需要覆盖时用 --force-with-lease（远程被人改过就拒绝，安全得多）。
  5. 不 commit 密码、密钥、.env。 一旦推到公开仓库，即使删掉，历史记录和 GitHub 的缓存里还在，需要当作泄露处理。
  6. 出了事先 git status 和 git reflog。 这两条能解决 80% 的"完了，救不回来了"。
