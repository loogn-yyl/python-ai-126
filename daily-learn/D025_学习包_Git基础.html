1心智模型：三个区，一串快照

Git 只做一件事：在你要的时候，把整个目录拍一张照片存起来。提交不是「记录改了什么」，是「存下此刻所有文件的完整样子」。理解这一点，后面所有命令都是在管理「照片放哪、拿哪张」。

工作区 暂存区 本地仓库 Working Tree → Index / Stage → Repository （你眼前的文件） （准备提交的清单） （一张张提交快照） │ │ │ │ git add │ git commit │ └───────────────────────┴──────────────────────┘ │ │ git push ▼ 远程仓库（GitHub）
区是什么怎么往里放东西
工作区你能用编辑器打开的那些文件直接改，随便改
暂存区一份「这次要提交什么」的清单git add 文件
本地仓库.git 目录里的一串提交git commit
为什么要「暂存」这么一道？因为你经常同时改了好几件事：修 bug、加功能、改错别字。暂存区让你挑着提交——先 git add 那个 bug 的文件、提交一次，再 add 功能的文件、再提交一次。提交历史一条一件事，将来查问题时才查得动。
这就是「gl 一把梭」的代价：git add -A 把所有改动塞进一个提交，历史里就只剩「学习记录 11-22」这种一句话。

提交是快照，不是差异

这一点决定了 git diff 要跟谁比。每个提交都指向一棵完整的文件树，所以任意两个提交之间都能比，不比邻居也能比。

提交 A ── 提交 B ── 提交 C ── 提交 D （完整树） （完整树） （完整树） （完整树） ▲ HEAD（你现在在哪）
HEAD 是「你现在站在哪个提交上」的指针。HEAD~1 是上一个，HEAD~3 是往前三个。它跟着分支走——你在 main 分支上提交，main 和 HEAD 一起往前挪。

git status --short：两列状态码，天天看

git status --short
git add app.py
git status --short
git commit -m "初始化项目"
git status --short
git log --oneline

码意思在哪一列
??未跟踪，git 完全不管它两列都是 ?
A新增，已暂存左列（暂存区）
M修改左列 = 已暂存；右列 = 只在工作区改过
D删除同上
UU冲突未解决两列都是 U
两列的含义是「左暂存、右工作区」，这是 --short 最需要先记住的一件事。M app.py 表示「暂存区有改动」， M app.py（M 在右边）表示「只在工作区改过、还没 add」。看到 M 就知道还差一个 git add；看到 M 就知道还差一个 git commit。
README.md 一直是 ??，说明它从来没被提交过。这是初学者最容易忽略的事——你以为的「项目已经进 Git 了」，其实只进了一半。git status 每次都要看，不是走过场。

提交信息怎么写

# 好的提交信息：一行说完这件事，必要时空一行写细节
git commit -m "日志工具支持 csv 输出"

# 需要写细节时用两个 -m
git commit -m "修复 GBK 日志解码失败" -m "read_text 之前写了没接上，现在按 utf-8 → gbk 顺序尝试"

# 改错了上一条（还没 push 时）
git commit --amend -m "新的信息"
判断标准：一年后的你看这条信息，能不能知道「当时为什么要改」。「update」「修改」「fix bug」都是无效信息——它们和「学习记录 11-22」是同一个问题：只记录了动作，没记录内容。
你的 gl 默认信息是「学习记录 MM-DD」，日常提交够用；但作品集的提交建议手写，因为那是要给别人看的。

3diff 的三个视角：到底在跟谁比

因为有三个区，所以「看差异」有三种比法。分不清的时候，画面图：比较的是左右相邻的两个格子。

工作区 ←─ git diff ─→ 暂存区 ←─ git diff --cached ─→ 仓库(HEAD)
# 改一下文件
echo "line2" >> app.py

git status --short          #  M app.py  ← M 在右边，说明只在工作区
git diff                    # 工作区 vs 暂存区

git add app.py
git diff                    # 空了！因为工作区和暂存区已经一样
git diff --cached           # 暂存区 vs HEAD（这次要提交的内容）
 M app.py

diff --git a/app.py b/app.py
index a29bdeb..c0d0fb4 100644
--- a/app.py
+++ b/app.py
@@ -1 +1,2 @@
 line1
+line2
git add 之后 git diff 变空，是新手的第一个「我的改动没了？！」惊吓时刻。改动没丢，只是从「工作区 vs 暂存区」的差异里消失了——两边现在一样了。用 git diff --cached 看它。
命令比较什么时候用
git diff工作区 ↔ 暂存区「我改了但还没 add 的东西」
git diff --cached暂存区 ↔ 最新提交commit 之前必看：确认这次到底要提交什么
git diff HEAD工作区 ↔ 最新提交「从现在到上次提交，一共变了什么」
git diff A B任意两个提交/分支「这两个版本差在哪」
提交前跑一次 git diff --cached，是一个能省掉很多麻烦的习惯。它能当场发现：误加进来的调试代码、忘了删的 print、不该提交的密钥、编辑器生成的临时文件。这些一旦提交再清理，就要多一次提交或者改写历史。

看历史：log 的四种看法

git log                     # 完整信息，翻页看
git log --oneline           # 一行一条
git log --oneline -5        # 最近 5 条
git log --oneline --graph   # 带分支图
git log --stat              # 每条改了哪些文件、多少行
git log -p app.py           # 某个文件的历史改动
git log --author="loogn" --since="7 days ago"
b47175a 合并 feature：保留日志与缓存两项
a423299 main: 加日志
95c148b feature: 加缓存
49cb2a5 初始化项目
git log --oneline --graph 是唯一能看清分支形状的方式，第 5 节合并完一定要跑一次。提交号那 7 位是哈希的前 7 位，唯一标识一个提交，可以当参数用：git diff a423299 b47175a。

4.gitignore：为什么加了规则，文件还在

.gitignore 只对「未跟踪的文件」生效。已经被提交过的文件，加进规则也不会被忽略——这是你的仓库 11-22 真实撞上的问题（day06/log.txt 第二次被提交进来）。

cd ~/git-lab/demo
echo "x" > log.txt
git add -A && git commit -m "误提交 log.txt"

printf '*.log\n' > .gitignore
git status --short
git check-ignore -v log.txt
?? .gitignore
（check-ignore 没有任何输出 —— 因为 log.txt 已被跟踪）
规则写了、文件还在、git status 里也不消失。因为忽略规则只回答一个问题：「这个从没被跟踪过的文件，要不要提醒我？」——已经跟踪的，规则管不着。规则生效后新加的文件才会被挡住，这也解释了为什么「加了 .gitignore 之后还是有垃圾进来」：那些垃圾是在规则之前或规则没覆盖到的路径下产生的。
# 正确做法：从索引里移除，但本地文件保留
git rm --cached log.txt
git status --short
ls log.txt
D  log.txt
?? .gitignore
log.txt
看第三行：文件还在。D 在左列表示「索引里删掉它」，这是要提交的改动；工作区的文件完全没动。
git rm --cached 和 git rm 的区别就是这一条：--cached 只动索引，不加才是连文件一起删。加错的那次，文件就真没了（除非在回收站/trash 里）。

写 .gitignore 的四条规则

写法含义例子
*.log任何目录下的 .log 文件日志、缓存
/*.txt只有根目录的 .txt根目录的临时文件
build/任何叫 build 的目录及其内容编译产物
!重要.log取反：放行必须写在被忽略规则之后
# 验证某条规则到底有没有生效（对未跟踪文件）
echo "z" > new.log
git check-ignore -v new.log
.gitignore:1:*.log	new.log
git check-ignore -v 输出三段：哪一行规则、规则内容、命中的文件。排查「为什么这个文件被忽略了 / 为什么没被忽略」用它最快——比逐条读 .gitignore 猜要快十倍，而且能告诉你别的 .gitignore 有没有插一脚（子目录里的 .gitignore 也会生效，还有全局的 ~/.gitignore）。
不要用 git add -f 强行把被忽略的文件加进来，尤其是在你已经写对了规则的情况下。那等于在规则上开一个洞，而且后来的人看不出为什么这个文件特殊。真要放行，就在 .gitignore 里显式写一条 !路径，并在旁边写一行注释说明为什么。

5分支：开一条线，做完再合回来

分支在 Git 里便宜得离谱——它只是一个指向某个提交的指针，40 个字节。所以「开个分支试试」永远比「在主分支上硬改」划算。

git branch                  # 看有哪些分支（* 是当前的）
git switch -c feature       # 新建并切过去（老版本 git 用 checkout -b）
git branch
git switch main             # 切回来
* main
  feature
git switch 是 git 2.23 之后的新命令，把 checkout 的两个职责拆开了：switch 管切分支、restore 管还原文件。老教程里的 git checkout -b 现在还能用，但新命令更不容易误操作。

合并的两种情况

情况一：快进（fast-forward） main: A ── B ╲ feature: C ── D 合并后 main 直接指到 D，不产生新提交。 情况二：三方合并（产生一个合并提交） main: A ── B ────── M ╲ ╱ feature: C ── D
git switch main
git merge feature
git log --oneline --graph
*   b47175a 合并 feature：保留日志与缓存两项
|\
| * 95c148b feature: 加缓存
* | a423299 main: 加日志
|/
* 49cb2a5 初始化项目
看图的方式：* 是提交、竖线是同一条分支、斜线是分叉/汇合。上面这张图的读法是：从 49cb2a5 分叉出两条，各自走了一个提交，然后在 b47175a 汇合。合并提交有两个父提交，这就是它和普通提交的唯一区别。
为什么这次必须产生合并提交、不能快进？因为两边都往前走了。快进只在「目标分支没有新提交」时才能发生——那种情况下 Git 连新提交都不用建，直接把指针挪过去。git merge --no-ff 可以强制产生合并提交，好处是历史里能看出「这里曾经有一个功能分支」。

6冲突：不是错误，是 Git 在问你「留哪个」

冲突的唯一原因是：同一个文件的同一片区域，两条分支改了不同的内容。Git 不敢替你决定，于是把两边都写进文件，等你选。

# 制造冲突：两条分支改同一行
git switch -c feature2
printf '项目说明\n版本：v1\n新增：缓存功能\n' > README.md
git add -A && git commit -m "feature: 加缓存"

git switch main
printf '项目说明\n版本：v2\n新增：日志功能\n' > README.md
git add -A && git commit -m "main: 加日志"

git merge feature2
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
git status --short
cat README.md
UU README.md

项目说明
<<<<<<< HEAD
版本：v2
新增：日志功能
=======
版本：v1
新增：缓存功能
>>>>>>> feature2
这三行标记必须整个删掉，不能只删一半。
<<<<<<< HEAD 到 ======= 之间 = 你当前分支（main）的内容
======= 到 >>>>>>> feature2 之间 = 要合进来的那条分支的内容
常见错误是只留自己要的那段，把标记漏在文件里——然后这个文件就跑不起来了，而且报错指向的行号会偏移，很难查。

解冲突的四个动作

# 1. 手工编辑，改成你想要的样子（两个都要，或者只留一个，或者重写）
printf '项目说明\n版本：v2\n新增：日志功能\n新增：缓存功能\n' > README.md

# 2. 标记为已解决
git add README.md

# 3. 看一眼没漏（此时 status 里不该再有 UU）
git status --short

# 4. 完成合并提交
git commit -m "合并 feature2：保留日志与缓存两项"
M  README.md
[b47175a] 合并 feature2：保留日志与缓存两项
关键理解：解冲突的「编辑」是普通编辑，不是 git 命令。Git 只负责把两边内容摆在你面前、并把状态标成 UU；你改完文件、git add 一下，就是告诉它「这个文件我处理过了」。git add 在这里的作用不是「加入版本库」，是「标记冲突已解决」——这就是为什么解完冲突必须 add，否则 git commit 会拒绝。
# 想放弃这次合并，回到合并前的样子
git merge --abort

# 想看看冲突的两边各自是什么（不切分支）
git diff --name-only --diff-filter=U     # 哪些文件冲突
git show :1:README.md                    # 共同祖先的版本
git show :2:README.md                    # 当前分支的版本
git show :3:README.md                    # 对方的版本
git merge --abort 是解冲突时的安全绳。改乱了、拿不准，直接 abort 回到干净状态，想清楚了再来一遍。它还顺手清掉工作区的冲突标记，不会有残留。

7回退：三种 reset 与一个更该用的 revert

这是 Git 里最容易造成实际损失的一组命令。先把三个层次摆清楚：移动分支指针、重置暂存区、还原工作区。

命令分支指针暂存区工作区文件用在哪
reset --soft HEAD~1后退不动不动提交信息写错、想重新提交
reset --mixed HEAD~1（默认）后退重置不动提交太早，想重新挑文件
reset --hard HEAD~1后退重置全部丢弃真的不要这些改动了
# 实测三种的差别（在一个一次性提交上试）
git reset --soft HEAD~1
git status --short        # M  README.md   ← 改动还在暂存区

git reset --mixed HEAD
git status --short        #  M README.md   ← 改动退回工作区

git reset --hard HEAD
git status --short        # （空）         ← 改动没了
--hard 会真的删掉工作区里没提交的改动，没有确认框。三个字的代价可能是半天的工作。规则：敲 --hard 之前，先 git status 看一眼，再用 git stash 存一下。
git stash 是「把当前改动临时收进抽屉」：git stash 收起、git stash pop 拿出来。不确定要不要丢的东西，一律先 stash，它比 reset --hard 便宜太多了。

已经 push 出去了，怎么撤

# 撤销某个提交，但保留历史（生成一个「反向提交」）
git revert a423299
git log --oneline -3
9c1b2f0 Revert "main: 加日志"
a423299 main: 加日志
49cb2a5 初始化项目
reset 改写历史，revert 追加历史。两者选哪个只看一件事：这个提交 push 过没有、别人有没有基于它工作。
push 过 → 用 revert。因为 reset 之后你本地历史跟远端不一致，要 push 就得 --force，而强推会把别人的提交冲掉。个人仓库只有你一个人用，强推问题不大；但只要有过协作，强推就是事故。

还原单个文件：restore 比 reset 安全

git restore app.py                 # 工作区的改动丢掉，回到暂存区版本
git restore --staged app.py        # 从暂存区撤出，改动留在工作区
git restore --source=HEAD~2 app.py # 回到两个提交前的版本
git restore 文件 只影响那一个文件，不影响分支指针，是「改坏了想重来」的首选。顺手记一下：git restore --staged 等价于老写法 git reset HEAD 文件——作用就是「取消 add」，不动文件内容。

8reflog：删错了也能找回来

Git 几乎不真的删东西。提交只要存在过，就会在 reflog（引用日志）里留一条记录，默认保留 90 天。reset --hard 之后觉得删错了，就靠它。

git reflog --oneline | head -n 6
b47175a HEAD@{0}: commit (merge): 合并 feature：保留日志与缓存两项
a423299 HEAD@{1}: commit: main: 加日志
49cb2a5 HEAD@{2}: checkout: moving from feature to main
95c148b HEAD@{3}: commit: feature: 加缓存
49cb2a5 HEAD@{4}: checkout: moving from main to feature
49cb2a5 HEAD@{5}: commit (initial): 初始化项目
# 救回来：找到那个提交号，开一个分支指过去
git switch -c rescue b47175a

# 或者直接把当前分支拉回去
git reset --hard b47175a
reflog 是 Git 的撤销键。它记录的是「HEAD 每次移动」，所以 merge、reset、rebase、switch 全都在里面。误删分支、硬回退过头、rebase 搞乱——都能从 reflog 里捞回来。
但有个前提：你得知道自己要找什么。所以养成一个习惯：做危险操作前，git log --oneline -3 记一下当前提交号，出事了直接指回去。
reflog 是本地记录，push 不上去，也不跟着仓库走。换台机器、重新 clone 就没有了。所以它救不了「昨天在另一台电脑上删掉的东西」。

9练习八道

全部在 ~/git-lab/demo 里做，别在 ~/python-learn 里练。

第 1 题 · 建仓库、提交两个文件、把第三个文件留在未跟踪状态

答案 
mkdir -p ~/git-lab/ex1 && cd ~/git-lab/ex1
git init
echo a > one.txt; echo b > two.txt; echo c > three.txt
git add one.txt two.txt
git commit -m "加入 one 和 two"
git status --short
?? three.txt

?? 就是「git 看着它，但不管它」。这种文件不会被提交、不会被 push、也不会在 diff 里出现——所以「我明明写了新文件，为什么远端没有」的答案永远是这一行。

第 2 题 · 只提交一个文件里的一部分改动

答案 
echo "第二行" >> one.txt
git add -p one.txt
# 交互里按 y 接受这个片段、n 跳过、q 退出
git diff --cached      # 确认暂存了什么
git commit -m "one.txt 加第二行"

git add -p（patch 模式）是「一个文件里改了三件事、只想提交其中一件」的唯一办法。它会一段一段问你，按 ? 能看到全部按键。
这个技能在真实项目里非常值钱——修 bug 时顺手改了格式、加了日志，用 -p 就能只提交修 bug 那部分。

第 3 题 · 让日志文件不被跟踪，且不影响已提交的那个

答案 
printf '*.log\n' >> .gitignore
git rm --cached log.txt
git add .gitignore
git commit -m "不再跟踪 log.txt，加 .gitignore"
git status --short
ls log.txt

顺序很重要：先改 .gitignore、再 git rm --cached、最后一次提交。只做 git rm --cached 而不加规则，下次 git add -A 它又回来了。
验证要看两处：git status 里不再出现它，ls 里文件还在。

第 4 题 · 建分支、改文件、合回主分支（能快进的那种）

答案 
git switch -c feat-1
echo "新功能" >> two.txt
git add two.txt && git commit -m "feat: two 加新功能"
git switch main
git merge feat-1
git log --oneline --graph
* 提交号 feat: two 加新功能
* 提交号 不再跟踪 log.txt，加 .gitignore
...

这次是快进：main 在分支创建后没有新提交，所以合并不产生新提交，指针直接挪过去。判断方法就是看图——没有分叉就没有合并提交。

第 5 题 · 制造一个冲突，然后放弃这次合并

答案 
git switch -c feat-2
echo "feat-2 的版本" > one.txt
git add -A && git commit -m "feat-2 改 one"

git switch main
echo "main 的版本" > one.txt
git add -A && git commit -m "main 改 one"

git merge feat-2
# 看到 CONFLICT 之后
git merge --abort
cat one.txt
main 的版本

--abort 之后 one.txt 回到了 main 的版本，冲突标记也清干净了。这比手工删标记可靠——手工删最容易漏掉 ======= 那一行。

第 6 题 · 提交信息写错了，还没 push，怎么改

答案 
git commit --amend -m "写对的信息"
git log --oneline -1

--amend 是「用一个新的提交替换上一个」，不是修改——提交号会变。所以只在还没 push 的时候用；push 过之后 amend 会造成本地和远端历史不一致，要同步就得强推。
顺便：--amend 不带 -m 时会打开编辑器，让你改信息。

第 7 题 · 硬回退之后发现删错了，救回来

答案 
git log --oneline -1        # 记下当前提交号
git reset --hard HEAD~1     # 假装删错了
git reflog --oneline | head -n 3
git reset --hard 刚才记下的提交号
git log --oneline -1

这一步的关键是「先记下提交号」——真实场景里你往往是删完才想救，那就从 reflog 里找：找 HEAD 移动之前那一条，格式是 HEAD@{1} 或直接写提交号。
以后做危险操作前跑一次 git log --oneline -1，成本两秒，救命。

第 8 题 · 看某个文件从建库到现在改过多少次、每次改了什么

答案 
git log --oneline -- one.txt
git log -p -- one.txt

-- 文件路径 前面那两个横线不能省：它把「路径」和「分支名」分开，避免同时存在一个叫 one.txt 的分支时产生歧义。
--follow 还能跟踪文件改名：git log --follow -p -- 新文件名。查「这段奇怪的代码是谁、什么时候、为什么加的」，就是用这条。

八题里第 5、6、7 是「出事之后怎么救」的三条：冲突能放弃、信息能改、历史能捞回。这三个练熟，你用 Git 就不会再怕操作。怕的根源从来不是命令难，是不知道错了能不能回头。
