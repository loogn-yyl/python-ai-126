今天的两个概念经常被讲得很玄，其实都很朴素。闭包 = 一个函数记住了外面变量的值；装饰器 = 一个函数接收另一个函数，包一层再返回。合在一起就是「不改函数内部，就能给它加上计时、重试、日志」。

1闭包：函数能记住外面的变量

def make_counter():
    count = 0

    def inner():
        nonlocal count
        count += 1
        return count

    return inner


c1 = make_counter()
print(c1(), c1(), c1())
c2 = make_counter()
print(c2())
print(c1())
1 2 3
1
4

看最后两行：c2() 是 1，说明 两次 make_counter() 各自有一份独立的 count；紧接着 c1() 是 4，说明 c1 那份一直被记着，没丢。

要素在这里是说明
外层函数make_counter创建并返回内层函数
内层函数inner用到外层的 count
闭包inner + 它捕获的 count函数 + 它记住的变量，一起被返回出去
nonlocalnonlocal count声明「我要改外层的那个 count」，不是新建一个
make_counter()() 立刻报错：UnboundLocalError: cannot access local variable 'count'
这就是 D005 讲过的 LEGB 规则：函数里只要出现 count = ... 这种赋值，Python 就认定 count 是局部变量，于是 count + 1 里的 count 还没赋值就被读了。加一行 nonlocal count 只是告诉 Python「别新建，用外层的那个」，和 global 是同一个道理，只是目标层级不同（global 找最外层，nonlocal 找外层函数）。
C 里没有闭包，但你有类似的直觉。static int count = 0; 在函数里也能跨调用保存值，区别是它只有一份，全局共享；闭包是每次调用外层函数就新建一份——这就是为什么 c1 和 c2 互不影响。想要「每个实例一份」的状态，C 里得靠传结构体指针，Python 用闭包就够了。

记住这一条就够了：@deco 只是 f = deco(f) 的语法糖。没有任何魔法。@ 之后，名字 hi 指向的已经不是原来那个函数，而是 wrapper。

为什么装饰器这么有用：计时、日志、重试、缓存、权限检查，这些逻辑和业务无关、但每个函数都要加。写进函数里会污染业务代码，复制粘贴又维护不了。装饰器让它们套在函数外面，被装饰的函数一个字都不用改。

3两个必踩的坑：参数丢失、名字丢失

坑一：wrapper 不接收参数

def deco(func):
    def wrapper():
        return func()

    return wrapper


@deco
def add(a, b):
    return a + b


print(add(1, 2))
TypeError: deco.<locals>.wrapper() takes 0 positional arguments but 2 were given

你调的是 add(1, 2)，但 add 现在指向 wrapper，而 wrapper 的定义是 def wrapper():——一个参数都不收。报错信息里的 deco.<locals>.wrapper 就是在提醒你「这是装饰器里那个 wrapper」。

def wrapper(*args, **kwargs):
    return func(*args, **kwargs)

标准答案就是这两个星号。*args 接所有位置参数，**kwargs 接所有关键字参数，原样转给 func。写装饰器时这两行默认就要写上，除非你明确只想装饰无参函数。

坑二：函数的名字和文档丢了

import functools


def deco_plain(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper


def deco_wraps(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper


@deco_plain
def a(x):
    """a 的文档字符串"""
    return x


@deco_wraps
def b(x):
    """b 的文档字符串"""
    return x


print("没有 wraps:", a.__name__, repr(a.__doc__))
print("有 wraps  :", b.__name__, repr(b.__doc__))

有 wraps  : b 'b 的文档字符串'

报错信息里显示的名字全是 wrapper，看不出是哪个函数真实函数名
help() / IDE 提示没有说明正常显示
这不是「讲究」，是排错时的实际成本。线上报错栈里出现十个 wrapper，你根本不知道是哪个函数出的问题。
规则：写装饰器一定加 @functools.wraps(func)，一行的事。

4带参数的装饰器：多套一层

想要 @repeat(3) 这种「装饰器自己也能带参数」的写法，就得再套一层函数：

import functools


def repeat(n):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            result = None
            for _ in range(n):
                result = func(*args, **kwargs)
            return result

        return wrapper

    return deco


@repeat(3)
def hello(name):
    print("hi", name)


hello("张三")
print(hello.__name__)

hi 张三

def repeat(n):              # 第 1 层：收装饰器的参数
    def deco(func):         # 第 2 层：收被装饰的函数
        @functools.wraps(func)
        def wrapper(*a, **kw):   # 第 3 层：收函数调用时的参数
            ...
        return wrapper
    return deco
层收什么什么时候执行
repeat(n)装饰器参数 3定义函数时（@repeat(3) 那一刻）
deco(func)被装饰的函数紧接着，同上
wrapper(*a)调用时的实际参数每次调用
判断要不要三层的方法：看 @ 后面有没有括号。
@timer → 两层（timer(func)）
@retry(3) → 三层（retry(3) 先执行，返回 deco，再由 deco(func) 收函数）
写错了会得到一个很典型的报错：TypeError: 'function' object is not callable——因为你少写了一层，Python 把函数当成了装饰器参数。

5类装饰器：用类来当装饰器

装饰器只要求「能被调用」，所以除了函数，一个实现了 __call__ 的对象也能当装饰器（D010 学过）。这样做的好处是：状态存得住。

import functools


class CountCalls:
    def __init__(self, func):
        self.func = func
        self.count = 0
        functools.update_wrapper(self, func)

    def __call__(self, *args, **kwargs):
        self.count += 1
        print(f"  第 {self.count} 次调用 {self.func.__name__}")
        return self.func(*args, **kwargs)


@CountCalls
def greet(name):
    return f"你好 {name}"


print(greet("张三"))
print(greet("李四"))
print("调用次数:", greet.count)
print(greet.__name__)
  第 1 次调用 greet
你好 张三
  第 2 次调用 greet
你好 李四
调用次数: 2
greet
函数装饰器类装饰器
怎么写三层函数嵌套__init__ 存 func + __call__ 调用
状态存哪要靠 nonlocal 或可变默认参数self.count，天然就有
名字要保留吗@functools.wrapsfunctools.update_wrapper(self, func)
什么时候用类装饰器：装饰器自己需要记状态、或者需要好几个配置项时。上面这个「统计调用次数」用函数也能写，但要用 nonlocal 绕一圈；用类就直白得多。真实项目里两种都能见到，读得懂就行，写的时候优先选简单的。

6三个能直接用的装饰器

这三个是日常最常用的，抄进自己的工具文件就能一直用。注意每个都以 @functools.wraps(func) 开头。

① timer —— 测耗时

import functools
import time


def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        used = (time.perf_counter() - start) * 1000
        print(f"  [{func.__name__}] 用时 {used:.2f} ms")
        return result

    return wrapper


@timer
def slow_sum(n):
    return sum(i * i for i in range(n))


print("结果:", slow_sum(1000000))
print("函数名还是:", slow_sum.__name__)
  [slow_sum] 用时 133.22 ms
结果: 333332833333500000
函数名还是: slow_sum
用 time.perf_counter() 而不是 time.time()：前者是单调时钟，专门用来测时长——系统时间被校准、被时区改动都不影响它。time.time() 会跳，测出来的数可能是负的。

② retry —— 失败重试

import functools


def retry(times=3):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for i in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except ValueError as e:
                    print(f"  第 {i} 次失败: {e}")
            print("  全部失败，放弃")
            return None

        return wrapper

    return deco


@retry(3)
def parse(text):
    return int(text)


print(parse("42"))
print(parse("abc"))
42
  第 1 次失败: invalid literal for int() with base 10: 'abc'
  第 2 次失败: invalid literal for int() with base 10: 'abc'
  第 3 次失败: invalid literal for int() with base 10: 'abc'
  全部失败，放弃
None
重试只对「可能会自己好的错」有意义。网络超时、接口限流、数据库锁等待 —— 这些重试有用。int("abc") 这种数据本身错了的，重试一百次也一样，纯属浪费。
还有一条纪律：必须设上限。没有上限的重试 = 死循环。
真实项目里还要加「间隔」——第一次失败立刻重试往往还是失败。标准做法是每次等待时间翻倍（退避）：0.1s → 0.2s → 0.4s。今天先把结构学会，加个 time.sleep(0.1 * i) 就是带间隔版。

③ log —— 不污染业务代码的日志

D013 的产出就靠它：通讯录的每个操作都自动记一行，而增删函数里一句日志代码都没有。

def log(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        with open("actions.log", "a", encoding="utf-8") as f:
            f.write(f"{func.__name__}({args[0]}) -> {result}\n")
        return result
    return wrapper
这就是装饰器最标准的用途：把「和业务无关」的事从业务函数里赶出去。看 add() 的函数体，只有「加一个人、返回结果」两件事，没有任何 open、write——它根本不知道有日志这回事。想改成写数据库、发消息、上报监控，只改装饰器，业务函数一动不动。

# D013 笔记

## 闭包
- 内层函数用到外层函数的变量，外层函数把这个内层函数返回出去
- 返回的是「函数 + 它记住的变量」
- 每次调用外层函数 → 一份新的状态，互不影响
- 改外层变量要写 nonlocal；不写会 UnboundLocalError（LEGB 规则）

## 装饰器本质
- @deco 等价于 f = deco(f)，没有任何魔法
- deco 收一个函数，返回一个新的函数（wrapper）
- @ 之后，名字指向的已经是 wrapper，不是原函数

## 两个必踩的坑
- wrapper 忘了 *args, **kwargs → TypeError: takes 0 positional arguments
- 忘了 @functools.wraps(func) → __name__ 变 wrapper、__doc__ 变 None、报错栈里认不出是谁

## 带参数的装饰器
- 三层：外层收装饰器参数，中层收 func，内层 wrapper 收调用参数
- 判断方法：@ 后面有括号就是三层

## 类装饰器
- 实现 __call__ 的类也能当装饰器
- 好处：状态存在 self 里，不用 nonlocal
- 名字保留用 functools.update_wrapper(self, func)

## 三个常用
- timer：time.perf_counter()（单调时钟，测时长用它，别用 time.time()）
- retry：只对「可能会自己好」的错重试；必须设上限；真实场景要加退避间隔
- log：把日志从业务函数里赶出去，业务函数完全不知道有日志

## 反直觉
- 生成器省内存，但不一定更快（有 yield 的开销）
- 选型看瓶颈：内存吃紧用生成器，求快就建列表
