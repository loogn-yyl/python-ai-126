六道自测题：答不上来就回去补那一天的笔记

  1. __eq__ 里 return False 和 return NotImplemented 有什么区别？
  2. 为什么 @dataclass 的 tags: list = [] 会在定义类的那一刻就报错？
  3. 生成器为什么只能遍历一次？list(gen) 之后再 for 为什么是空的？
  4. @deco 之后，函数名指向的还是原来那个函数吗？
  5. 类属性里放一个列表，所有实例共享同一份，应该怎么改？
  6. is 和 == 分别该在什么时候用？
六道题的答案（先自己答，再对）

1. 两者的区别是「我不知道」，不是「不相等」。
False 表示「我比较过了，结论是不相等」，比较到此结束；NotImplemented 表示「我不会跟这种类型比，你让别人试试」——Python 会去调对方的 __eq__，两边都放弃才退回到 is。
判断条件上有个坑：NotImplemented 是真值，if not result: return False 写不出正确的语义，必须写 if result is NotImplemented。

2. 因为 dataclass 会检查默认值是不是可变对象。
类属性在定义类时只创建一次，所有实例共享它——一个人 tags.append，所有人的 tags 都变了。dataclass 干脆在生成 __init__ 时直接抛 ValueError: mutable default <class 'list'> for field tags is not allowed，逼你用 field(default_factory=list)——每次创建实例都调一次 list()，各拿各的。

3. 因为生成器函数体的状态只有一份。
yield 会把函数「冻」在当前这一行，等你下次 next() 才继续。走到 return 之后就再也回不去了，再 for 只能拿到空。
要重复用就先存下来：data = list(gen)，代价就是 D012 说的内存。

4. 不是。@deco 完全等价于 f = deco(f)，名字 f 现在指向的是 装饰器里返回的那个 wrapper。原函数还在，只是没名字指向它了（除非你把它存起来）。

5. 搬进 __init__ 里，或者用 field(default_factory=list)。
self.tags = [] 写在 __init__ 里，就是每个实例一份新的。dataclass 里则写 tags: list = field(default_factory=list)。

6. == 比「值」，is 比「是不是同一个对象」。
日常都用 ==。必须用 is 的只有几种情况：和 None 比（x is None）、和 True/False 比、和 NotImplemented 比。
为什么必须：你可以让 __eq__ 返回任何东西，但一个对象「是不是 None」这件事没有含糊余地。

校验放 __post_init__，不覆盖 __init__

想在创建时检查数据，直觉是重写 __init__。但 dataclass 已经生成好了 __init__，覆盖它意味着你要把四个字段的赋值全部手写一遍——那用 dataclass 就白用了。正确位置是 __post_init__：它在生成的 __init__ 末尾被自动调用一次。

    def __post_init__(self):
        if not self.name.strip():
            raise ValueError("姓名不能为空")
        if not (self.phone.isdigit() and len(self.phone) == 11):
            raise ValueError(f"电话必须是 11 位数字: {self.phone}")

cases = [("  ", "13800001111"), ("张三", "138"), ("张三", "1380000111a")]

        Contact(*args)

为什么在「造出来的时候」就报错，比在后面某个函数里检查好？
因为错误离原因越近越好。Contact("张三", "138") 这一行直接炸，你就知道是这里传错了；如果放过去，等你第二天读 json 时才发现格式不对，根本查不到是哪一步写进去的。
这条规矩叫「快速失败」：宁可启动就崩，也不要带着坏数据跑三天。
注意 name.strip() 那个写法：只判 if not self.name 挡不住 " "（两个空格字符串）。用户输入里这种「看着有、其实没有」的值特别多，去掉首尾空格再判空是必备动作。

存进 json 再读回来：to_dict / from_dict

json 只认识字典、列表、字符串、数字——不认识 Contact 对象。所以进出各要一次转换，这两个方法就放在 models.py 里，因为它们只关心「一个人怎么变成数据」，跟存哪儿无关。

back = Contact.from_dict("张三", d)
print("存进去再读回来一样吗:", back == c)

v1 旧格式: Contact(name='李四', phone='13900002222', email='', tags=[])

三个细节值得看：
① asdict() 把 dataclass 递归转成字典，但结果里没有 name——因为 to_dict() 里 pop 掉了。姓名在 json 里是键（{"张三": {...}}），不用再存一遍。
② back == c 是 True——D010 学的 __eq__ 在这里派上用场：没有它，两个内容一样的对象比出来是 False。
③ from_dict 里有个 isinstance(d, str) 分支，专门兼容 v1 的老格式（姓名 → 电话字符串）。这叫向后兼容：老用户手里的 contacts.json 不能因为升级就废掉。

4存储层：装饰器加在哪一层，是个判断题

先看效果——三段操作，日志自动出来，而 add 的函数体里没有一行跟日志有关的代码：

    @log
    def add(self, contact):
        if contact.name in self.items:
            raise ValueError(f"{contact.name} 已存在")
        self.items[contact.name] = contact
        self.save()
        return f"已添加 {contact.name}"

为什么 @log 加在 store 层，不加在 models 层？

如果加在……会发生什么结论
Contact 的方法上「造一个联系人」被记一次日志。可造对象不等于改通讯录——校验失败重试三次会记三条日志，实际什么都没发生日志记录的是「操作」，不是「数据」
AddressBook.add/remove 上一次成功的增删记一条，跟用户视角完全一致选它
save() 上一次 add 里 save 只调一次，看着也行；但以后批量导入时 save 会被调很多次，日志就乱了装饰器要加在「用户视角的一个动作」上
装饰器的粒度问题，判断标准就一句：日志里的一行，应该对应「用户做的一件事」。用户点「添加」，日志就该多一行；用户在输入框里删了又改、最后校验没过，日志不该多三行。
这是设计问题，不是语法问题——写得出装饰器之后，更难的是决定往哪儿放。

别为了「像容器」把方法加满。__getitem__、__len__、__iter__ 各有明确语义，加了就得对；__add__ 这种「两个通讯录相加」看着酷，实际没人会用，还容易写出语义混乱的代码。只加你真的会调用的。

5pytest 入门：把「跑一下看着对」变成「自动检查」

先看昨天的做法有多脆：写一段 if c.name != "张三": print("错了")，跑一遍，看到没打印「错了」就认为对。问题有三个：改完代码要重新看一眼；忘了看就漏了；没法一次检查三十个条件。

手写 if / printpytest
怎么表示「对」if ...: print("错了")assert 条件，不成立就抛异常
怎么知道全过了肉眼看输出结尾一行 N passed
失败时看到什么你自己 print 的那句话哪一行、实际值、期望值、涉及的表达式
怎么只跑一个没有这个概念文件末尾加 ::测试名
一百个用例不可维护自动收集，文件名以 test_ 开头、函数以 test_ 开头

第三步：测「应该报错」这件事

正常路径好测，报错路径很多人就跳过不测了。pytest 给了 pytest.raises，专门断言「这里必须炸」：

第二个测试失败，恰恰证明测试在正常工作。DID NOT RAISE 的意思是「代码正常跑完了，没抛异常」——而你断言它应该抛。所以测试失败的信息是：校验没生效。
反过来说：如果代码炸了但你没写 pytest.raises，测试同样会失败（异常会一路冒出来）。所以「测异常」和「测正常」的区别，就是外面包不包这一层。

为什么一定要测报错路径：校验逻辑只有两种结果，「该过的过」和「该拦的拦住」。只测前者，等于只验证了一半。
真实事故里，绝大多数是该拦的没拦住——脏数据进了库，三天后才发现。

第四步：fixture —— 每个测试都要一个干净的通讯录

麻烦来了：AddressBook 一创建就会 load()，add() 会 save()。如果所有测试共用 contacts.json，上一个测试写进去的人会被下一个测试读到。看这个对照：

from contacts import AddressBook, Contact

for i in (1, 2):
    book = AddressBook(path="shared.json")
    print(f"第 {i} 次打开，已有 {len(book)} 条")
    book.add(Contact(f"用户{i}", "13800001111"))
第 1 次打开，已有 0 条
第 2 次打开，已有 1 条

第 2 次「打开」已经不是空的了。这不是 bug，是文件本来就是持久的。但测试要的是每次从零开始，否则assert len(book) == 0 这种断言就永远在碰运气——取决于你之前跑过什么。

@pytest.fixture把「准备环境」这段抽出来，测试函数写个参数名就能用每个测试各执行一次，互不影响
tmp_pathpytest 给每个测试新建一个空目录，用完自动清写文件不污染你的项目目录，也不用自己 os.remove
monkeypatch临时改掉某个属性，测试结束自动改回来LOG 是模块级变量，改了影响全局，必须能还原
不写隔离的后果，比你想的严重：
① 测试有时过有时不过，你开始怀疑人生；
② 测试跑完发现项目里多了一堆 contacts.json、actions.log，还被 git status 提示；
③ 最坑的是顺序依赖——单独跑第 5 个测试通过，跑全套就失败。这种 bug 能查一整天。
规矩：凡是要读写文件的测试，必须先要一个 tmp_path。

完整的测试文件里，第一个def test_之前的这一小段就是全部准备工作。九个测试，三次 pytest.raises，一次存盘往返，一次读日志——覆盖了 v3 该有的行为：

def test_添加后能查到(book):
    book.add(Contact("张三", "13800001111"))
    assert len(book) == 1
    assert book.find("张")[0].name == "张三"


def test_存盘再读回来(book, tmp_path):
    book.add(Contact("张三", "13800001111", "zs@example.com"))
    again = AddressBook(path=str(tmp_path / "contacts.json"))
    assert len(again) == 1
    assert again.items["张三"].email == "zs@example.com"
注意 test_存盘再读回来 这个测试的写法：它不检查 book.save() 有没有被调用，而是新开一个 AddressBook 去看数据在不在。
这是测试的一条重要原则：验证「结果」，别验证「过程」。你要是 mock 了 save 再断言「它被调用了一次」，那即使 save 里写的是 json.dump({})，测试照样通过。

两处值得细看

第 7 题的结论比答案本身重要。FileNotFoundError 是从装饰器里抛出来的，但它把整个 add 都带崩了——联系人没加进去。
真实项目里日志、监控、埋点这类「附加动作」绝不能影响主流程，正确写法是把写日志包起来：

def log(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        try:
            with open(LOG, "a", encoding="utf-8") as f:
                f.write(f"{func.__name__}: {result}\n")
        except OSError:
            pass          # 日志写不进去就算了，业务不能受影响
        return result
    return wrapper

第 8 题的 capfd 值得记住。用 print 输出提示信息的地方，测试要怎么验？答案是把标准输出「抓」下来：capfd.readouterr() 返回两个值，第一个是 stdout，第二个是 stderr。
out, _ = capfd.readouterr() —— 那个下划线就是「我不关心 stderr」。然后 assert "数据文件损坏" in out。
更规范的做法是把print 换成 logging，测试用 caplog——这是下下周的内容。

如果第 8 题最后停在 99%，大概率是 store.py:39 的 __iter__ 还没被跑到。因为有 __iter__ 不等于有测试在用它——补一句 assert [c.name for c in book] == ["张三"] 就够了。
这个过程本身就是在教你怎么读 Missing 那列。

# D014 笔记 · 第 2 周复盘与通讯录 v3

## 第 2 周六天一句话
- D008 类：数据 + 操作放在一起；忘写 self 会报 takes 1 positional argument
- D009 继承：父类定契约，子类换实现；组合优于继承
- D010 魔法方法：__str__ 给人看，__repr__ 给调试看；改 __eq__ 要连 __hash__
- D011 dataclass：自动生成 __init__/__repr__/__eq__；可变默认值用 default_factory
- D012 生成器：一次一个，省内存；只能走一遍
- D013 装饰器：@deco 就是 f = deco(f)；必写 *args/**kwargs + functools.wraps

## 项目分层
- models.py：数据长什么样 + 校验 + 进出字典        （不许 open）
- store.py ：能做什么（增删查、存盘读盘）
- decorators.py：跟业务无关的横切逻辑（日志）
- __init__.py：__all__ 白名单，对外只开一扇门
- 判断标准：能不能单独测

## 数据模型
- dataclass 四行顶手写三个方法
- 校验写 __post_init__，不覆盖 __init__（覆盖了等于放弃 dataclass）
- 快速失败：创建时就报错，别带着坏数据跑
- 判空要 name.strip()，纯空格字符串挡不住
- to_dict 用 asdict()；from_dict 要兼容旧格式（向后兼容）

## 装饰器加在哪一层
- 日志记录的是「操作」，不是「数据」→ 加在 store 层，不加 models 层
- 加在 save() 上会失控（批量导入时一次操作记很多行）
- 一行的粒度 = 用户做的一件事
- 附加动作（日志/监控）绝不能被它们影响主流程：包 try/except

## pytest
- 文件名 test_*.py，函数名 test_*，不写 main
- assert 条件，不成立就抛异常；assert 后面写一句人话
- 读报错：> 是出错行，E assert 11 == 10 是实际 vs 期望，
  E + where 11 = len(...) 是中间值怎么来的
- pytest.raises(ValueError)：断言这里必须炸；没炸就 FAILED: DID NOT RAISE
- fixture：抽公共准备；每个测试各执行一次
- tmp_path：每个测试一个空目录，用完自动清 —— 读写文件必须用
- monkeypatch：临时改属性，测试结束自动还原
- 验证结果，别验证过程（别 mock save 再断言它被调用）

## 覆盖率
- Stmts 语句数 / Miss 没跑到 / Cover 比例 / Missing 哪几行 ★
- 真正该看的是 Missing —— 那是「没被测过的代码清单」
- 87% → 90%（补坏 json 分支）→ 100%（补 line、旧格式、__iter__）
- 100% 不等于没 bug：只说明被执行过，不说明断言过结果
- 没有 assert 的测试能刷满覆盖率，但保护力是零
