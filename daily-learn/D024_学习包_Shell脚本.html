今天的判断标准不是「语法对不对」，是「这个脚本别人拿去能不能直接跑」。三个具体指标：路径不能写死（用 $1 或 $HOME）、出错要停（set -euo pipefail）、每一步要有日志（不然跑失败了不知道卡在哪）。这三点做到，脚本就及格了。
shell 脚本和 Python 的分工，先划清楚：超过 100 行、要处理数据结构、要写单元测试 → 用 Python。而「串几条命令、定时跑、部署后执行一次」→ 用 shell。用 shell 写业务逻辑是自找麻烦，它的长处是「调度别的程序」，不是「计算」。

1第一个脚本：三行就够，但有四个细节

mkdir -p ~/linux-lab/sh && cd ~/linux-lab/sh
cat > hello.sh <<'EOF'
#!/bin/bash
# 我的第一个脚本
echo "当前目录：$(pwd)"
echo "参数个数：$#"
EOF
chmod 755 hello.sh
./hello.sh
当前目录：/Users/loogn/linux-lab/sh
参数个数：0
细节为什么必须
第一行 #!/bin/bash告诉系统用哪个解释器。不写的话，./x.sh 会用当前 shell 的默认解释器跑，在别人的机器上可能变成 sh（功能更少）
chmod 755没有 x 位就只能 bash x.sh，不能 ./x.sh（昨天的权限知识）
<<'EOF' 里的单引号让 EOF 里的 $ 不被展开，原样写进文件。去掉引号，$(pwd) 会在写入时就被求值，脚本里存的是一句死字符串
echo "..." 带引号不带引号时，多个空格会被压成一个，* 会被展开成文件名（昨天第 5 节）

三种执行方式，行为不一样

方式发生什么什么时候用
./hello.sh起一个新进程，用 shebang 指定的解释器正常执行脚本都用这个
bash hello.sh起一个新 bash 进程，忽略 shebang调试，或脚本没有 x 权限时
source hello.sh在当前 shell 里跑，变量和函数会留在当前会话要加载配置（source ~/.zshrc）
第三种会污染你的当前会话。脚本里如果写了 cd /tmp，用 source 执行完之后，你的终端就停在 /tmp 了，而 ./ 执行不会。这就是为什么改了 .zshrc 之后要 source ~/.zshrc——它必须影响当前会话，否则新加的别名不生效。

macOS 的 bash 是 3.2，2007 年的版本

bash --version | head -n 1
GNU bash, version 3.2.57(1)-release (x86_64-apple-darwin23)

这个版本号意味着网上一半的「bash 教程」会跑不通。下面这些是 4.0 以后才有的，在 macOS 自带 bash 里会报 bad substitution 或 command not found：

写法作用macOS 3.2 怎么办
${var^^} / ${var,,}转大写 / 小写用 tr '[:lower:]' '[:upper:]'
declare -A map关联数组（字典）没有，改用两个平行数组或干脆用 Python
mapfile -t arr < f把文件读成数组用 while read -r line; do ...; done < f
cmd &>> log追加 stdout+stderr用 cmd >> log 2>&1
${var,,} 之类的花活大小写转换同上，用 tr
两个选择：① 把脚本写成 3.2 兼容的（推荐，因为你写的脚本多半还要拿到 Linux 服务器上跑，而服务器上的 bash 通常更新，兼容 3.2 就两边都能跑）；② brew install bash 装新版，脚本第一行写 #!/opt/homebrew/bin/bash——但这样脚本就只能在你的 Mac 上跑了。
今天所有示例都是 3.2 兼容写法，你照抄不会踩坑。

2变量：三条规则，一个必须背下来的坑

赋值时不能有空格

name="loogn"        # 对
count=3             # 对
# name = "loogn"    # 错！shell 会把 name 当成命令名去执行
dir=/tmp/mydir
echo "$name 有 $count 个文件，目录 $dir"
loogn 有 3 个文件，目录 /tmp/mydir
name = "loogn" 报的错是 name: command not found，不是「语法错误」。因为 shell 把这一行理解成「执行一个叫 name 的命令，参数是 = 和 loogn」。赋值和比较在 shell 里长得太像，这是所有人第一个踩的坑。
判断规则：等号两边有空格 = 比较/命令；没空格 = 赋值。

$var 和 ${var}：什么时候必须加花括号

file="report"
echo "$file.txt"        # 正常：点不是变量名字符，$file 到点就结束
echo "$file_2026"       # 出错：shell 去找一个叫 file_2026 的变量（不存在）
echo "${file}_2026"     # 正确：花括号划清边界
report.txt

report_2026
第二行不报错，只是输出一个空行。变量名允许包含字母、数字、下划线，所以 $file_2026 里 shell 认为变量名是 file_2026，拿到空值；而 $file.txt 里的点号不是变量名字符，反而正好是安全的。
习惯：只要变量后面紧跟字母、数字、下划线，一律写 ${}。加括号永远不会错。文件名拼接的场合尤其容易忘："backup-${name}-${stamp}.tar.gz"。

命令替换与算术

today=$(date +%Y-%m-%d)
n=$(ls | wc -l | tr -d ' ')
echo "今天 $today，当前目录有 $n 项"

a=7
b=2
echo $((a / b))        # 整数除法
echo $((a % b))
echo $((a * b))
今天 2026-11-22，当前目录有 3 项
3
1
14
$(( )) 只能算整数。要做小数得用 awk 或 bc：echo "7/2" | bc -l 得到 3.50000000000000000000。这一条和 D001 的 7 / 2 == 3 是同一个道理——shell 的算术比 Python 还简陋，别指望它算浮点。
tr -d ' ' 是干嘛的：wc -l 在某些系统上输出带前导空格（" 3"），直接塞进字符串会多出空格，做数字比较时可能出错。删掉空格最省事。

默认值与只读

log_dir="${LOG_DIR:-$HOME/logs}"
echo "$log_dir"

readonly MAX=7
# MAX=8   # 会报 MAX: readonly variable

echo "脚本名 $0"
echo "第一个参数 ${1:-（没给）}"
echo "参数个数 $#"
/Users/loogn/logs
脚本名 ./vars.sh
第一个参数 （没给）
参数个数 0
${VAR:-默认值} 是 shell 里最实用的语法之一：变量没设时用默认值，设了就用变量。它让「不传参数也能跑」这件事变成一行，不用写 if 判断。
相关的还有 ${VAR:=默认值}（没设时顺便赋值）、${VAR:?错误信息}（没设就报错退出）。最后一个在必填参数上特别好用：SRC="${1:?用法: backup.sh 源目录}"。

3条件判断：[ ] 里的空格不是排版，是语法

f=~/linux-lab/logs/access.log

if [ -f "$f" ]; then
  echo "是文件，行数：$(wc -l < "$f")"
else
  echo "不存在：$f"
fi

if [ -d ~/linux-lab ]; then echo "目录存在"; fi
if [ -z "${UNSET_VAR}" ]; then echo "变量是空的"; fi
是文件，行数：5
目录存在
变量是空的
[ -f "$f" ] 里每个空格都不能少。[ 是一个命令（等价于 test），它必须收到 ] 作为最后一个参数。写成 [-f "$f"] 会报 [-f: command not found。
还有一条："$f" 的引号必须加。变量为空时，不加引号会变成 [ -f ]——只收到一个参数，测试结果永远是「真」，你的判断形同虚设。

常用的判断条件

对文件对字符串对数字
-e 存在-z "$s" 为空-eq 等于
-f 是普通文件-n "$s" 非空-ne 不等
-d 是目录"$a" = "$b" 相等-lt 小于
-r 可读 / -w 可写 / -x 可执行"$a" != "$b" 不等-gt 大于
数字比较不能用 < >，字符串比较不能用 -eq，这两条会静默出错。[ 10 < 9 ] 会被当成「重定向」，在当前目录建一个叫 9 的文件然后返回真。所以 shell 里数字一律用 -eq/-lt/-gt，字符串一律用 = !=。

[ ] 和 [[ ]] 的区别

[ ]（POSIX test）[[ ]]（bash 内建）
变量为空时会崩，必须加引号安全，不加引号也行
&& ||不行，要写 -a -o可以
正则 =~不支持支持
可移植性所有 sh 都认只有 bash/zsh 认
今天统一用 [[ ]]，因为文件头写的是 #!/bin/bash，bash 一定有它。网上很多教程用 [ ] 是为了兼容 #!/bin/sh——但 sh 在 macOS 上是 bash 3.2 的兼容模式，在 Ubuntu 上是 dash，行为不一致，所以别写 #!/bin/sh。
用 [[ ]] 之后，变量不加引号也安全，这是它最大的好处：[[ -f $f ]] 在 $f 为空时是「假」，不会崩也不会永远真。

case：多重判断比 if-elif 干净

mode="${1:-text}"
case "$mode" in
  text|csv)  echo "输出格式：$mode" ;;
  json)      echo "输出格式：JSON" ;;
  -h|--help) echo "用法: demo.sh [text|csv|json]" ;;
  *)         echo "不认识的参数：$mode" >&2; exit 2 ;;
esac
;; 是 case 的分隔符，每个分支结尾都要有。* 分支相当于 else，处理未知参数一定要有它，并 exit 2——退出码 2 是「用法错误」的约定，和 D020 的 argparse 一致。

逐行读文件：while read 才对

# 对：一次读一行，保留空格
while IFS= read -r line; do
  echo "[$line]"
done < ~/linux-lab/logs/access.log

# 错：for 会把每一行按空格切成词
for line in $(cat ~/linux-lab/logs/access.log); do
  echo "[$line]"
done | head -n 3
[2026-11-20 10:00:01 GET /index.html 200 512]
[2026-11-20 10:00:05 POST /api/login 401 88]
...（共 5 行，每行完整）
[2026-11-20]
[10:00:01]
[GET]
for line in $(cat 文件) 是 shell 里最经典的错误写法。命令替换会把输出按空格和换行切开，于是每一行被拆成 6 个词，循环跑了 30 次而不是 5 次。而且它看起来「能跑」，只是结果错得离谱。
正确写法三件套：while IFS= read -r line; do ...; done < 文件
· IFS= 防止行首行尾空格被吃掉
· -r 防止反斜杠被转义
· < 文件 放在 done 后面，不要用 cat 文件 | while ...——管道会让循环在子 shell 里跑，循环里设的变量外面读不到
# 反例：管道版，变量留不下来
count=0
cat ~/linux-lab/logs/access.log | while read -r line; do
  count=$((count + 1))
done
echo "管道版数出来：$count"

# 正例：重定向版
count=0
while read -r line; do
  count=$((count + 1))
done < ~/linux-lab/logs/access.log
echo "重定向版数出来：$count"
管道版数出来：0
重定向版数出来：5
这个差异非常隐蔽：两个版本都能「正常结束」，只是第一个的计数丢了。原因是管道右边的 while 在子 shell 里执行，改的是子 shell 的 count，父 shell 的还是 0。任何「循环里累加、循环后用」的写法，都不能用管道。

脚本参数：$1 $@ $# shift

cat > args.sh <<'EOF'
#!/bin/bash
echo "脚本名：$0"
echo "参数个数：$#"
echo "全部参数（带引号）：$@"
echo "第一个：$1"
shift
echo "shift 之后第一个：$1"
EOF
bash args.sh one two three
脚本名：args.sh
参数个数：3
全部参数（带引号）：one two three
第一个：one
shift 之后第一个：two
"$@" 和 $@ 的区别，是 shell 里最细也最重要的一处：带引号时，每个参数保持独立（"one" "two"）；不带引号时，会被重新按空格切分。转发参数时一律写 "$@"——这是唯一能完整传递「参数个数和内容」的写法。
$* 则会把所有参数拼成一个字符串，需要「把它们当成一个整体」时才用，实战里很少。记一条就够：函数或脚本转发参数，写 "$@"。

5函数：返回值不是值，是退出码

cat > func.sh <<'EOF'
#!/bin/bash
log() {
  local level="$1"; shift
  printf '[%s] %-5s %s\n' "$(date +%H:%M:%S)" "$level" "$*"
}

is_log_file() {
  [[ "$1" == *.log ]]
}

log INFO "开始处理"
if is_log_file "access.log"; then
  log INFO "是日志文件"
else
  log WARN "不是日志文件"
fi
log ERROR "演示一条错误"
EOF
bash func.sh
[19:30:01] INFO  开始处理
[19:30:01] INFO  是日志文件
[19:30:01] ERROR 演示一条错误
return 只能返回 0–255 的整数，而且它是「退出状态」，不是「返回值」。想返回一段文本，用 echo 输出，调用方用 $(函数名) 接：
get_size() {
  du -sh "$1" | cut -f1
}
size=$(get_size ~/linux-lab/logs)
echo "logs 大小：$size"
logs 大小：5.0K
两条约定，建议从今天起固定下来：
① 函数内部变量一律加 local，否则会污染全局，几个函数共用一个变量名时互相踩。
② 「函数成功/失败」靠 return 0/1，配合 if 函数名; then 使用；「函数产出什么」靠 echo。这两件事分开，脚本才读得懂。
上面那个 log() 函数建议直接抄进你的所有脚本——local level="$1"; shift 这一手是把第一个参数取出来、剩下的全交给 $*，是 shell 里处理「可选前缀参数」的标准写法。

6健壮性：让脚本出错就停，而不是错着跑完

这一节比前面五节加起来更能决定你的脚本能不能给别人用。默认情况下，shell 遇到错误会继续往下执行——删错了目录照样往下跑，备份失败了照样报告「完成」。

三个开关，写在脚本第二行

#!/bin/bash
set -euo pipefail
开关作用不开会怎样
-e任何命令失败（退出码非 0）立即退出错误被忽略，后面的步骤在错误状态上继续跑
-u用未定义的变量就报错退出$UNSET 展开成空，拼出一个像 /backup/.tar.gz 的怪路径
-o pipefail管道里任何一个命令失败，整条算失败昨天讲过：ls nope | head 报成功
set -e 有几个「管不到」的地方，必须知道：
① 在 if 条件里的命令失败不会退出（这是特性，不然 if grep ... 就没法用了）；
② cmd || true 结尾的命令不算失败；
③ 管道只有最后一个命令的退出码会被检查，除非加了 pipefail。
所以 set -e 不是万能的——关键步骤还是要自己写 if ! 命令; then 处理。

trap：不管怎么退出，都把临时文件清掉

cat > trap-demo.sh <<'EOF'
#!/bin/bash
set -euo pipefail

TMPFILE=$(mktemp)
trap 'rm -f "$TMPFILE"; echo "退出时清理：$TMPFILE"' EXIT

echo "临时文件：$TMPFILE"
echo "数据" > "$TMPFILE"
ls -l "$TMPFILE"
EOF
bash trap-demo.sh
临时文件：/var/folders/xx/.../T/tmp.AbC123
-rw-------  1 loogn  staff  5 Nov 22 19:35 /var/folders/xx/.../T/tmp.AbC123
退出时清理：/var/folders/xx/.../T/tmp.AbC123

验证 trap 真的生效：把输出里那个路径复制出来，ls -l 那个路径，应该报 No such file or directory——脚本退出时它被删掉了。

mktemp 是唯一正确的临时文件写法——它生成一个不重名的路径并创建文件。不要写 TMP=/tmp/mydata.txt：两个实例同时跑就互相覆盖，还可能因为别人预先建好同名文件而被利用（符号链接攻击）。
trap ... EXIT 的意思是「脚本无论怎么结束（正常、报错、Ctrl+C）都执行这句」，这是保证「不给系统留垃圾」的标准做法。D027 部署脚本里会用到同样的结构。
到这里，一个「可以交给别人」的脚本就有雏形了：set -euo pipefail 打底、mktemp + trap 处理临时文件、log() 函数输出过程。剩下的就是具体业务——也就是下面那个备份脚本。

7写 backup.sh：分四步，每步都能单独验

别一次写完再跑。按下面四步走，每步加一小块、跑一次看结果。这样出错时你知道是哪一块的问题。

第 1 步 · 骨架 + 参数

mkdir -p ~/linux-lab/bin && cd ~/linux-lab/bin
cat > backup.sh <<'EOF'
#!/bin/bash
set -euo pipefail

SRC="${1:-$HOME/python-learn}"
DEST="${2:-$HOME/backups}"
KEEP="${KEEP:-7}"

log() { printf '[%s] %s\n' "$(date +%H:%M:%S)" "$*"; }

log "源目录：$SRC"
log "备份到：$DEST"
log "保留份数：$KEEP"
EOF
chmod 755 backup.sh
./backup.sh
[19:40:02] 源目录：/Users/loogn/python-learn
[19:40:02] 备份到：/Users/loogn/backups
[19:40:02] 保留份数：7
注意 KEEP="${KEEP:-7}" 和 DEST="${2:-...}" 的区别：KEEP 从环境变量取（可以 KEEP=3 ./backup.sh），DEST 从第二个位置参数取。前者适合「偶尔调一下」的配置，后者适合「每次都要指定」的输入。不区分的话，参数一多就乱了。

第 2 步 · 加打包

cat > backup.sh <<'EOF'
#!/bin/bash
set -euo pipefail

SRC="${1:-$HOME/python-learn}"
DEST="${2:-$HOME/backups}"
KEEP="${KEEP:-7}"
STAMP=$(date +%Y%m%d-%H%M%S)
NAME="backup-$(basename "$SRC")-$STAMP.tar.gz"

log() { printf '[%s] %s\n' "$(date +%H:%M:%S)" "$*"; }

[[ -d "$SRC" ]] || { log "错误：$SRC 不是目录"; exit 1; }

mkdir -p "$DEST"
log "开始打包 $SRC"
tar -czf "$DEST/$NAME" \
    --exclude="__pycache__" \
    --exclude=".git" \
    --exclude="*.pyc" \
    -C "$(dirname "$SRC")" "$(basename "$SRC")"
log "完成：$DEST/$NAME ($(du -h "$DEST/$NAME" | cut -f1))"
EOF
./backup.sh
[19:42:11] 开始打包 /Users/loogn/python-learn
[19:42:15] 完成：/Users/loogn/backups/backup-python-learn-20261122-194211.tar.gz (1.2M)
[[ -d "$SRC" ]] || { ...; exit 1; } 这一行值得单独看：它等价于「如果不是目录，就打印错误并退出」。花括号里的最后一条命令后面必须有 ;，倒数第二条也必须有——这是 shell 花括号的语法要求，少一个就报错。
为什么用 -C "$(dirname "$SRC")" 而不是直接 tar -czf out.tar.gz "$SRC"：直接打绝对路径，包里会带完整的 /Users/loogn/... 层级，解压时还原出一串嵌套目录。先 cd 到上一级、用相对名打包，解压出来才是干净的。

第 3 步 · 清理旧备份

cat >> backup.sh <<'EOF'

COUNT=$(ls -1 "$DEST"/backup-*.tar.gz 2>/dev/null | wc -l | tr -d ' ')
log "现有 $COUNT 个备份，保留最近 $KEEP 个"
if [[ "$COUNT" -gt "$KEEP" ]]; then
  ls -1t "$DEST"/backup-*.tar.gz | tail -n +$((KEEP + 1)) | while read -r old; do
    rm -f "$old"
    log "删除旧备份 $(basename "$old")"
  done

8crontab：让脚本自己按时跑

backup.sh 现在要手动执行。定时任务的意义是「你忘了它也会跑」，这也是它危险的原因——写错的定时任务会每天删一次你的东西。

五个字段，顺序别记反

* * * * * 要执行的命令 │ │ │ │ │ │ │ │ │ └── 星期几（0–7，0 和 7 都是周日） │ │ │ └───── 月（1–12） │ │ └──────── 日（1–31） │ └─────────── 小时（0–23） └────────────── 分钟（0–59）
想什么时候跑写法
每天凌晨 3:000 3 * * *
每 6 小时一次0 */6 * * *
每周一 9:3030 9 * * 1
每月 1 号 0:055 0 1 * *
每 5 分钟*/5 * * * *
crontab -l                 # 看现在有什么（第一次会报 no crontab）
crontab -e                 # 编辑
crontab -l                 # 编辑完再确认一遍

加进去的内容长这样（绝对路径，不能写 ~/）：

# 每天 03:00 备份 python-learn
0 3 * * * /Users/loogn/linux-lab/bin/backup.sh /Users/loogn/python-learn /Users/loogn/backups >> /Users/loogn/backups/cron.log 2>&1
cron 环境和你终端里的环境几乎完全不同，这是定时任务失败的第一原因。三条必须遵守：
① 路径写绝对路径。cron 不会加载 ~/.zshrc，你的 PATH、别名、gl 函数全都不存在。
② 命令里的每个可执行文件最好都用绝对路径，或者脚本开头自己 export PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin。
③ 一定要把输出重定向进日志文件（上面的 >> cron.log 2>&1）。cron 默认会把输出发邮件，而你的机器没有邮件服务，结果就是「什么都没发生」，连报错都看不到。

macOS 上的额外两关

  • cron 需要「完全磁盘访问权限」。如果脚本要读你的家目录下的文件，需要到「系统设置 → 隐私与安全性 → 完全磁盘访问权限」里把 cron 加上。不加的表现是脚本能跑、但读到的目录是空的。
  • Mac 更适合用 launchd（~/Library/LaunchAgents/ 下的 plist）。cron 在 macOS 上能用，但苹果更推荐 launchd，而且笔电睡眠时会错过触发时间，launchd 有「错过后补跑」的配置。今天先用 crontab 学会五个字段的含义，真要在 Mac 上做长期定时任务，D027 之后再考虑 launchd。
# 验证：先设一个每分钟跑的测试任务，确认真的会触发
* * * * * /bin/date >> /tmp/cron-test.log 2>&1
# 等两分钟，然后
cat /tmp/cron-test.log
# 确认能跑之后，把这个测试任务删掉（crontab -e 里删那一行）
「先设一个只写时间的测试任务」，是配置定时任务的标准第一步。它把「cron 有没有在工作」和「我的脚本对不对」两个问题分开了——不然任务没跑起来，你会以为是脚本写错了，查半天。

9练习八道

前四道是语法，后四道是「真场景」。每道都跑一遍再点答案。

第 1 题 · 写一个脚本，接受一个目录参数，输出里面有多少个 .py 文件

答案 
cat > count_py.sh <<'EOF'
#!/bin/bash
set -euo pipefail
dir="${1:?用法: count_py.sh 目录}"
[[ -d "$dir" ]] || { echo "不是目录：$dir" >&2; exit 1; }
n=$(find "$dir" -name "*.py" -type f | wc -l | tr -d ' ')
echo "$dir 下有 $n 个 .py 文件"
EOF
chmod 755 count_py.sh
./count_py.sh ~/linux-lab
/Users/loogn/linux-lab 下有 2 个 .py 文件

${1:?...} 是必填参数的写法：没传参就打印这条消息并退出（退出码 1），比你自己写 if 判断少三行。
tr -d ' ' 不能省，否则 n 里带前导空格。

第 2 题 · 判断一个文件是不是「今天改过」的

答案 
f=~/linux-lab/logs/access.log
if [[ -n "$(find "$f" -mtime -1 2>/dev/null)" ]]; then
  echo "最近一天内改过"
else
  echo "超过一天没动"
fi

find 文件 -mtime -1 在「一天内改过」时会输出文件名，否则什么都不输出——用 -n 判断输出是否为空，就得到了布尔值。
这是 shell 里做「有没有」判断的通用套路：命令有输出 = 有，输出为空 = 没有。别去找「判断文件时间的运算符」，它不存在。

第 3 题 · 遍历一组目录，跳过不存在的，打印每个的大小

答案 
for d in ~/python-learn ~/linux-lab ~/nope; do
  if [[ ! -d "$d" ]]; then
    echo "跳过（不存在）：$d" >&2
    continue
  fi
  echo "$(basename "$d") $(du -sh "$d" | cut -f1)"
done
python-learn 1.2M
linux-lab 5.0K
跳过（不存在）：/Users/loogn/nope

大小数字随你的目录变，格式才是重点：basename 取最后一段目录名、du -sh | cut -f1 取大小。continue 跳过本轮、break 跳出整个循环，这两个别混。
把「跳过」的消息写到 >&2（stderr），这样正常的输出进管道时不会混进异常信息——昨天讲过的分流原则。

第 4 题 · 用 case 写一个简单的参数解析

答案 
while [[ $# -gt 0 ]]; do
  case "$1" in
    -v|--verbose) VERBOSE=1; shift ;;
    -o|--output)  OUT="$2"; shift 2 ;;
    -h|--help)    echo "用法: $0 [-v] [-o 文件]"; exit 0 ;;
    *)            echo "未知参数：$1" >&2; exit 2 ;;
  esac
done
echo "verbose=${VERBOSE:-0} output=${OUT:-（未指定）}"

shift 2 是因为 -o 吃掉了两个参数（选项本身 + 它的值）。忘记 shift 会导致死循环——$# 永远不变，while 永不结束。这是手写参数解析最常见的 bug，遇到卡住先查 shift。
参数超过三个、或者需要 --key=value 形式时，别手写——脚本里调 Python 的 argparse 更省事（D020 就是干这个的）。

第 5 题 · 统计一个目录里各个扩展名各有多少个文件

答案 
find ~/linux-lab -type f | sed 's/.*\.//' | sort | uniq -c | sort -rn
# 你的目录里数字会不同，格式是这样（次数在前，扩展名在后，按次数倒序）：
      4 log
      3 py
      3 txt
      2 md

sed 's/.*\.//' 是「删掉最后一个点之前的所有内容」，剩下的就是扩展名。.* 是贪婪匹配，会匹配到最后一个点——所以 a.b.txt 得到 txt 而不是 b.txt。
没有扩展名的文件会被算成一个「整路径」的怪键，真实目录里要加一层过滤：grep -v '/'。

第 6 题 · 让脚本在失败时清理临时目录并打印失败行号

答案 
#!/bin/bash
set -euo pipefail
TMPDIR_X=$(mktemp -d)
cleanup() {
  local rc=$?
  rm -rf "$TMPDIR_X"
  if [[ $rc -ne 0 ]]; then
    echo "失败于第 ${BASH_LINENO[0]} 行，退出码 $rc" >&2
  fi
}
trap cleanup EXIT

trap ... EXIT 在正常退出和报错退出时都会执行，所以要在里面判断 $? 区分两种情况。注意先存 local rc=$?——rm 一执行，$? 就被覆盖了。
${BASH_LINENO[0]} 在 bash 3.2 里可用，但它给的是「触发 trap 的那一层的行号」，不一定是出错那一行——精确行号要靠 set -E + trap ... ERR 配合。够用就好，别为这个折腾太久。

第 7 题 · 写一个「部署后自检」脚本：检查目录存在、端口通、进程在跑

答案 
#!/bin/bash
set -uo pipefail     # 故意不加 -e：要跑完所有检查再汇总

fail=0
check() {
  local name="$1"; shift
  if "$@" >/dev/null 2>&1; then
    printf '  OK   %s\n' "$name"
  else
    printf '  FAIL %s\n' "$name"; fail=1
  fi
}

check "静态目录存在"   test -d /var/www/html
check "80 端口在监听"  nc -z 127.0.0.1 80
check "nginx 进程在跑" pgrep -x nginx

[[ $fail -eq 0 ]] && echo "全部通过" || { echo "有检查未通过"; exit 1; }

这里故意不加 set -e：自检脚本的价值是「一次性告诉我哪些挂了」，如果第一个失败就退出，你只能一个个改一个个重跑。什么时候该关掉 -e，就看「是不是要收集全部问题」。
check() 那个 "$@" 是把剩余参数整条当命令执行——这是写「通用检查器」的标准手法。D027 部署完会直接用到它。

第 8 题 · 给 backup.sh 加上「锁」，防止上一次还没跑完就又启动

答案 
LOCK="/tmp/backup.lock"
if ! mkdir "$LOCK" 2>/dev/null; then
  echo "已有备份在跑，本次跳过" >&2
  exit 1
fi
trap 'rmdir "$LOCK"' EXIT

mkdir 是原子操作——两个进程同时执行，只有一个能成功，另一个报「已存在」。用一个目录当锁，比自己判断「有没有锁文件」可靠（后者有竞态窗口）。
为什么必须有锁：定时任务每小时跑一次、而某次备份因为数据变大跑了 90 分钟，就会出现两个备份进程同时打包，同时写同一个文件名，最后一个把前一个覆盖成半截文件——你会在恢复的时候才发现备份是坏的。

八题里第 4、6、8 是「从能跑升级到能放心用」的三道门槛。第 4 题决定你的脚本接不接得住参数，第 6 题决定失败时你查不查得出来，第 8 题决定它会不会在某个半夜自己搞坏自己。个人小工具可以不管，但一旦挂了定时任务，这三个都得有。
