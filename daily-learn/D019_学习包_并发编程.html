1四条路，一张表选完

方式怎么开适合代价
asyncioasync/awaitIO 密集、任务特别多（上千个连接）整条链路都得改成异步，同步库用不了

三个任务、每个 10 毫秒，写成线程池反而更慢——创建线程的开销比你省下的时间还多。今天第 4 节会用实测数据证明这一点。
并发是优化手段，不是代码风格。没测过变快，就别加。
为什么异步只适合「任务特别多」？
因为它在一个线程里管理所有任务，每个任务的额外开销只有几十字节。一万个并发请求，asyncio 扛得住，线程池会直接把内存吃光——每个线程默认要占几 MB 栈空间。
反过来，只有几十个任务时，用线程池写起来快得多，不值得为它改造整条链路。

2threading：最朴素的写法，和它的三个麻烦

先看最原始的多线程，目的是让你知道 futures 替你省了什么。

import threading
import time

results = []


def fetch(i):
    time.sleep(0.05 * i)
    results.append(f"任务{i}完成")


threads = [threading.Thread(target=fetch, args=(i,)) for i in range(1, 4)]

for t in threads:
    t.start()
for t in threads:
    t.join()          # 等所有线程结束

print("结果:", results)
print("线程还活着吗:", any(t.is_alive() for t in threads))
结果: ['任务1完成', '任务2完成', '任务3完成']
线程还活着吗: False

三个麻烦，每一个 futures 都解决了：

麻烦threading 的做法futures 的做法
拿返回值没有返回值。得自己往一个共享 list 里塞，或者用 queue.Queuepool.map() 直接给你一个列表
等结束必须 start() 一轮、join() 一轮，两轮循环with 块结束时自动等
抓异常异常在子线程里抛出，主线程完全不知道，只在终端打一行 tracebackf.result() 会把异常重新抛到调用方
第三条最坑。子线程里报错，主线程会若无其事地继续跑，你看到的结果就是「少了几条，但不报错」。
这是多线程排查难度高的根本原因——错误和它的后果发生在不同的地方。
join() 那一轮循环不能省。
少了它，主线程可能在子线程还没跑完时就 print(results)，你得到空列表或半个列表。而且这个错时有时无——机器快的时候看着对，换台机器就错。
更隐蔽的是：主线程退出时，非守护线程会被强制终止（daemon=False 时 Python 会等待，但行为依版本而异）。老老实实 join()。

3concurrent.futures：一个接口，两种池

这是实际项目里该用的东西。把 Thread 换成 Process，其他代码一个字都不用改——这是它最大的价值。

import time
from concurrent.futures import ThreadPoolExecutor

URLS = [f"https://site{i}.com" for i in range(1, 6)]
DELAY = 0.1


def fetch(url):
    time.sleep(DELAY)          # 模拟网络等待
    return f"{url} 的标题"


t0 = time.perf_counter()
serial = [fetch(u) for u in URLS]
print(f"串行   : {time.perf_counter() - t0:.1f} 秒")

t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    parallel = list(pool.map(fetch, URLS))
print(f"线程池 : {time.perf_counter() - t0:.1f} 秒")

print("结果一致:", serial == parallel)
print("第一条  :", parallel[0])
串行   : 0.5 秒
线程池 : 0.1 秒
结果一致: True
第一条  : https://site1.com 的标题

五行改动，快五倍，结果一字不差。这就是 futures 该有的样子。

map 和 submit 的区别

pool.map(f, xs)pool.submit(f, x)
返回结果迭代器，按输入顺序一个 Future 对象
拿结果直接 list()f.result()（阻塞等某个）
拿顺序永远是输入顺序用 as_completed() 按完成顺序
异常遍历到那一条时才抛f.result() 时抛
额外参数只能传一个可迭代对象可以传任意多个参数
怎么选？
「一批数据，同一个函数」→ map，一行搞定。
「要边完成边处理」或「参数不止一个」→ submit + as_completed。
map 看起来更简单，但它有个隐患：结果迭代器是惰性的，你不消费它，任务也会跑，但异常可能被吞掉。所以要么 list(pool.map(...)) 一次收完，要么用 submit。
with 语句结束时，池会等所有任务完成。
这意味着 with 块里的代码会「卡住」直到全部跑完。这是好事（保证不会提前退出），但如果你在 with 里写了个死循环任务，程序就永远退不出去。executor.shutdown(wait=False) 可以不等，但一般没必要。

4实测：什么时候并发反而更慢

这一段是本课最重要的内容。同样是并发，IO 密集和 CPU 密集的结果完全相反。

IO 密集：线程池有效

上面那个例子已经证明了——0.5 秒变 0.1 秒。因为等待的时候线程会让出 GIL，五个线程真的同时在等。

CPU 密集：线程池几乎无效，进程池也不一定

import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def cpu_work(n):
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 4_000_000
TASKS = [N, N]

if __name__ == "__main__":
    t0 = time.perf_counter()
    r1 = [cpu_work(n) for n in TASKS]
    print(f"单线程   : {time.perf_counter() - t0:.2f} 秒")

    t0 = time.perf_counter()
    with ThreadPoolExecutor(max_workers=2) as pool:
        r2 = list(pool.map(cpu_work, TASKS))
    print(f"线程池 2 : {time.perf_counter() - t0:.2f} 秒")

    t0 = time.perf_counter()
    with ProcessPoolExecutor(max_workers=2) as pool:
        r3 = list(pool.map(cpu_work, TASKS))
    print(f"进程池 2 : {time.perf_counter() - t0:.2f} 秒")

    print("结果一致:", r1 == r2 == r3)
单线程   : 0.80 秒
线程池 2 : 0.70 秒
进程池 2 : 1.27 秒
结果一致: True
看清楚这个结果：线程池只快了 0.1 秒，进程池反而慢了 0.47 秒。
为什么进程池更慢？因为 Windows 和 macOS 的 Python 用 spawn 方式启动子进程——每个子进程都要重新启动一个 Python 解释器、重新 import 模块，这个开销在 0.3~0.5 秒量级。你的任务只有 0.4 秒，省下的时间全被启动成本吃掉了，还倒贴。
方式为什么这个结果
线程池没变快GIL。两个线程抢一把锁，同一时刻只有一个在算，还多了切换开销
进程池更慢启动成本 > 收益。每个子进程都要重新初始化解释器
那什么时候进程池真的有用？判断标准只有一条：单个任务要跑得够久。
经验上，单个任务超过 0.5 秒，进程池开始划算；超过 2 秒，加速比接近核数。
所以你该做的是：先测，再决定。把 N 从 4_000_000 改成 40_000_000 再跑一次，你会看到进程池明显胜出——但那就说明「任务太碎」才是瓶颈，不是并发不够。
顺带说清 if __name__ == "__main__": 为什么必须有。
子进程启动时会重新 import 你的模块。如果没有这个守卫，模块顶层的代码会被再执行一遍，包括「创建进程池」这一行——于是子进程又去创建子进程，无限递归，Python 会直接报 RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase。
用线程池不需要它，用进程池必须有。

5GIL 保护不了你的变量

很多人有个误解：「有 GIL，所以多线程是安全的」。完全不对。

GIL 保证的是「同一时刻只有一个线程在执行字节码」，但它不保证「一段代码会连续执行完」——线程可以在两条字节码之间被切换掉。

而 counter += 1 在底层是三步：读、加、写。中间被切走，就会丢更新。

import threading
import time

N = 2_000
counter_nolock = 0
lock = threading.Lock()
counter_lock = 0


def add_nolock():
    global counter_nolock
    for _ in range(N):
        v = counter_nolock
        time.sleep(0)              # 把「读」和「写」之间的窗口放大
        counter_nolock = v + 1


def add_lock():
    global counter_lock
    for _ in range(N):
        with lock:
            v = counter_lock
            time.sleep(0)
            counter_lock = v + 1


ts = [threading.Thread(target=add_nolock) for _ in range(4)]
for t in ts:
    t.start()
for t in ts:
    t.join()

ts = [threading.Thread(target=add_lock) for _ in range(4)]
for t in ts:
    t.start()
for t in ts:
    t.join()

print("期望值:", 4 * N)
print("无锁结果正确:", counter_nolock == 4 * N)
print("有锁结果正确:", counter_lock == 4 * N)
期望值: 8000
无锁结果正确: False
有锁结果正确: True
time.sleep(0) 那两行是故意加的。
真实场景里，这个窗口只有几微秒，大多数时候你运气好，跑一万次都不出错。但只要机器慢一点、任务多一点、换个 Python 版本，它就会在某天凌晨三点爆一次。
加 sleep(0) 是为了把窗口放大到「一定能复现」，让你亲眼看到问题存在，不是问题只在加了 sleep 时才存在。

正确写法有四种，按推荐程度排

写法什么时候用
根本别共享首选。每个任务自己算自己的，结果放返回值和 map 里
queue.Queue生产者-消费者模型，队列内部已经加锁
threading.Lock不得已才用。锁的范围越小越好
dataclasses.replace / 不可变对象函数式写法，从根上避免修改共享状态
加了锁不等于没问题。
锁的经典错误是死锁：线程 A 拿了锁 1 等锁 2，线程 B 拿了锁 2 等锁 1，两边都不放，程序永久卡住。避免方法：所有地方都按同一个顺序拿锁，或者干脆只用一把锁。
更隐蔽的是锁粒度过大——把整个函数包起来，等于把并发变回串行，还不如不用线程。

6实战：多线程批量下载器

今天的产出。比起「能下载」，更重要的是它怎么处理失败。

import time
from concurrent.futures import ThreadPoolExecutor, as_completed

URLS = [f"https://site{i}.com/file{i}.zip" for i in range(1, 6)]


def download(item):
    i, url = item
    time.sleep(0.05 * i)                 # 越靠后越慢，让完成顺序可预期
    if "site3" in url:
        raise ConnectionError("连不上 site3")
    return f"{url} -> {100 * i} 字节"


def batch(urls, workers=3):
    ok, fail = [], []
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(download, it): it[1] for it in enumerate(urls, 1)}
        for f in as_completed(futures):
            url = futures[f]
            try:
                ok.append(f.result())
                print(f"完成 {url}")
            except Exception as e:
                fail.append(url)
                print(f"失败 {url} ({type(e).__name__})")
    return ok, fail


ok, fail = batch(URLS)
print()
print(f"成功 {len(ok)} 个，失败 {len(fail)} 个")
print("失败清单:", fail)
完成 https://site1.com/file1.zip
完成 https://site2.com/file2.zip
失败 https://site3.com/file3.zip (ConnectionError)
完成 https://site4.com/file4.zip
完成 https://site5.com/file5.zip

成功 4 个，失败 1 个
失败清单: ['https://site3.com/file3.zip']

三个设计决策，每一个都可以单独考你：

写法为什么
{submit(...): url for ...}字典把 Future 映射回 URL。as_completed 只给你 Future，不告诉你它是谁
try/except 在循环里必须在这里。放到 with 外面，第一个失败就会中断整批
fail.append(url)失败清单是产出的一部分。只报「成功 4 个」这种话，等于没说
as_completed(futures) 传的是字典，遍历出来的却是 Future。
传字典时它遍历的是键（也就是 Future），所以 futures[f] 能拿回 URL。这是 Python 里一个很常用的小技巧：用字典同时维护「对象 → 元信息」的映射。
注意别写成 futures.items()——那样 as_completed 会拿到元组，直接报错。
这个结构能直接改成 D017 的抓标题脚本。
把 download 换成 fetch_title，把 sleep 换成 requests.get，就是并发版抓取器。明天 D020 会在这个基础上加命令行参数和日志。

第 4 题 · 让异常抛回来

from concurrent.futures import ThreadPoolExecutor


def boom():
    raise ValueError("子线程炸了")


with ThreadPoolExecutor(max_workers=1) as pool:
    f = pool.submit(boom)
    try:
        f.result()
    except ValueError as e:
        print("主线程抓到了:", type(e).__name__, e)
主线程抓到了: ValueError 子线程炸了

这就是 futures 最值钱的地方之一。异常被存在 Future 对象里，你调 result() 时才重新抛出——而且抛出点就在你调用的那一行，调用栈是完整的。

第 5 题 · 线程池的甜点

import time
from concurrent.futures import ThreadPoolExecutor

DELAY = 0.1
TASKS = [DELAY] * 5

for w in (1, 2, 5, 10):
    t0 = time.perf_counter()
    with ThreadPoolExecutor(max_workers=w) as pool:

max_workers=1 就是串行（0.5 秒），这是最好的对照组。

第 6 题 · 用队列替代锁

import queue
import threading

N = 2_000
q = queue.Queue()
done = []


def worker():
    subtotal = 0
    while True:
        item = q.get()
        if item is None:
            q.task_done()
            break
        subtotal += item
        q.task_done()
    done.append(subtotal)


threads = [threading.Thread(target=worker) for _ in range(4)]
for t in threads:
    t.start()

for _ in range(N * 4):
    q.put(1)
for _ in range(4):
    q.put(None)          # 每个线程一个毒丸

q.join()
for t in threads:
    t.join()

print("总计数:", sum(done))
print("正确:", sum(done) == N * 4)
总计数: 8000
正确: True

核心思路是「不共享」：每个线程维护自己的 subtotal，最后再汇总。没有共享变量，就不需要锁——这是并发编程里最干净的写法。
「毒丸」None 是让阻塞在 q.get() 上的线程退出的标准手法。不发毒丸，q.join() 会永远等下去。

第 7 题 · 带进度的下载器

import time
from concurrent.futures import ThreadPoolExecutor, as_completed

URLS = [f"file{i}.zip" for i in range(1, 6)]


def download(item):
    i, url = item
    time.sleep(0.02 * i)
    return f"{url} 下载完成"


total = len(URLS)
with ThreadPoolExecutor(max_workers=3) as pool:
    futures = {pool.submit(download, it): it[1] for it in enumerate(URLS, 1)}
    for n, f in enumerate(as_completed(futures), 1):
        print(f"已完成 {n}/{total}  {f.result()}")

已完成 2/5  file2.zip 下载完成
已完成 3/5  file3.zip 下载完成
已完成 4/5  file4.zip 下载完成
已完成 5/5  file5.zip 下载完成

这里的进度计数是安全的，因为 enumerate 跑在主线程的循环里——只有一个线程在动它。如果把计数写进 download() 里，就要考虑加锁了。

第 8 题 · 限流

import time
from concurrent.futures import ThreadPoolExecutor

TASKS = list(range(1, 7))


def job(i):
    print(f"  开始 {i}")
    time.sleep(0.1)
    print(f"  结束 {i}")


with ThreadPoolExecutor(max_workers=2) as pool:
    list(pool.map(job, TASKS))

  结束 1
  结束 2

  结束 6

数一下「开始」和「结束」的排布：永远是两个开始、两个结束。这就是 max_workers=2 在起作用——第三个任务得等前两个里有空的。
这个输出格式是最好的自检工具：如果你看到六个「开始」连着出现，说明限流没生效。

你机器上的顺序会有细微差别。
比如「开始 3」和「结束 2」谁先谁后是不确定的——任务 1 先结束就立刻接手任务 3，可能赶在任务 2 打印之前。要看的不是具体顺序，是「同时有几个在跑」。

# D019 笔记 · 并发编程

## 四条路
asyncio               IO 密集、任务特别多（上千）   整条链路要改
ThreadPoolExecutor    IO 密集、已有同步代码          并发度受池大小限制
ProcessPoolExecutor   CPU 密集                        启动贵、参数要能 pickle
不用                   任务 ≤3 个或每个都很快          没有

## 判断标准
IO 密集（等）  → 线程池 / asyncio，真的会快
CPU 密集（算） → 多进程，且单任务要 > 0.5 秒才划算
任务很碎       → 并发开销 > 收益，比串行还慢 ★

## threading 的三个麻烦（futures 都解决了）
1 拿返回值：得自己塞共享 list
2 等结束  ：start 一轮 + join 一轮
3 异常    ：★子线程抛异常，主线程完全不知道，程序照样跑完
            少了几条数据，但界面上一切正常

## futures
pool.map(f, xs)      结果迭代器，★永远按输入顺序
pool.submit(f, x)    Future，f.result() 拿值/抛异常
as_completed(fs)     按完成顺序
{f: meta for ...}    ★字典把 Future 映射回 URL（as_completed 只给 Future）
★ 用 ProcessPool 必须 if __name__ == "__main__":，否则无限递归

## 实测结论（本机，4M 次循环 × 2）
单线程   0.80 秒
线程池 2 0.70 秒   ← GIL，几乎没提升
进程池 2 1.27 秒   ← ★反而更慢！spawn 启动成本 > 收益
→ 进程池单任务 > 0.5 秒才划算，> 2 秒接近核数
→ 先测再决定，别凭感觉加并发

## 竞态
counter += 1 是 读-加-写 三步，中间会被切
★GIL 只保证「同一时刻一个线程执行字节码」，不保证「一段代码连续执行完」
无锁 → 丢更新；有锁 → 正确
正确写法优先级：不共享 > queue.Queue > Lock > 不可变对象
死锁：A 拿锁1等锁2，B 拿锁2等锁1 → 统一加锁顺序

## 纪律
- 并发是优化手段，不是代码风格；没测过变快就别加
- 失败要收集清单，只报「成功 4 个」等于没说
- 自检：assert 串行结果 == 并发结果
