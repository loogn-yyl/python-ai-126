两个必须记住的相反结论

一、chmod 在 Git Bash 里是装饰品。
实测：一个文件 chmod 700 之后再 ls -l，权限位仍然显示 -rw-r--r--；从 Windows 侧 os.stat().st_mode 看是 0o666。命令不报错、退出码 0，但什么都没改——因为 NTFS 根本没有 Unix 权限位这套东西。
所以D023 的权限一节必须在 Mac（或真 Linux）上做，在 Windows 上练只会练出一个错误印象。
二、两台机器的命令血统是反的。
Mac 是 BSD，第 6 节那张差异表里「BSD 列」才是你要的；Git Bash 是 GNU（sed 4.9、ls 8.32、date -d 都能用），那张表对它正好反过来读。
最实用的用法：网上抄到一条命令，先在 Mac 上试，报错了再想「是不是 GNU 写法」。别拿 Windows 上跑通的写法去 Mac 上直接提交。
不要把网上抄来的 sudo rm -rf 粘进终端就回车。今天会出现好几次 rm -r，规则只有一条：敲完先不按回车，从左往右读一遍路径。删错东西没有回收站，/Volumes 和 ~ 之间只差几个字符。

2目录结构：文件到底放在哪

Unix 的世界只有一个树根 /，没有 C 盘、D 盘那种「盘符」。你需要记住的只有下面这些。

/ ← 根，所有路径的起点 ├── Users/ │ └── loogn/ ← 你的家目录，写作 ~ 或 $HOME │ ├── python-learn/ ← 你的代码在这儿 │ ├── Desktop/ Documents/ Downloads/ │ └── .zshrc ← 以点开头 = 隐藏文件 ├── Applications/ ← .app 都在这 ├── Library/ ← 系统和 App 的配置、缓存（别手删） ├── System/ ← 系统本体（别碰） ├── private/ │ ├── etc/ → /etc ← 全局配置（软链接） │ ├── tmp/ → /tmp ← 临时文件，重启可能清空 │ └── var/ │ └── log/ → /var/log ← 系统日志 ├── opt/homebrew/ ← Apple Silicon 上 Homebrew 装的东西 ├── usr/ │ ├── bin/ ← 系统命令（ls、grep 都在这） │ └── local/bin/ ← 手动装的东西 └── Volumes/ ← 外接硬盘、DMG 挂载点
Linux 服务器上会长得不一样：家目录是 /home/用户名、配置文件在 /etc/nginx/、网站文件常放 /var/www/、日志在 /var/log/nginx/。D027 部署时你会天天和这三个目录打交道，今天先记住形状。
Windows 的 Git Bash 又是另一种形状：没有 /var，每个盘单独挂成 /c、/d，家目录在 /c/Users/你的名字。你在那儿建 ~/linux-lab，实际落在 C:\Users\你的名字\linux-lab。

du 那两个数在你机器上不会是 8.0K，也不是任何固定值——因为它数的是「磁盘占用」，不是「文件有多少字节」。文件在磁盘上按块分配，一个 209 字节的日志也要占满一整个 4K 块，所以 logs 里两个文件报 8.0K，src 里两个 .py 也报 8.0K。块多大由文件系统决定：macOS 的 APFS 是 4K，Windows 的 NTFS 簇大小不同，同一份文件两边 du 出来能差一倍以上。
所以要分清两个问题：问「这个文件到底多少字节」用 ls -l 或 wc -c；问「它占了我多少盘」才用 du。内容大小和占用空间是两件事，1 个字节的文件也占 4K。
自己验证：printf 'a' > small.txt; ls -l small.txt; du -h small.txt —— 前者说 1 字节，后者说 4.0K。
顺序和格式是固定的：uniq -c 把计数放在前面，sort -rn 按数字倒序。注意 uniq 只能合并「相邻」的重复行——不先 sort 就直接 uniq -c，散落各处的同一个值会被算成好几份。这个坑几乎人人踩一次。

4find 与 grep：真正拉开差距的两个命令

别的命令是「操作已知的文件」，这两个是「在不知道文件在哪、也不知道内容长什么样的时候找到它」。真实工作里 80% 的时间花在这上面。

find 的四个维度

参数按什么找例子

-typef 文件 / d 目录 / l 软链接find . -type d
-mtime多少天内改过（-1 = 一天内）find . -name "*.py" -mtime -1
-size大小（+10M = 大于 10MB）find . -size +10M

-exec ... {} \; 是 find 的「对每个结果执行一条命令」，{} 是占位符，\; 是结束标记（分号必须转义，否则被 shell 吃掉）。
结果多时用 + 代替 \; 更快——find . -name "*.py" -exec wc -l {} + 会把所有文件名攒成一条命令，只启动一次 wc。两者输出格式略有不同（+ 会多一行 total），但结果一样。
cd ~/linux-lab
find . -name "*.py" | xargs wc -l
 1 ./src/main.py
 1 ./src/utils/helper.py
 2 total
xargs 和 -exec 的区别，一句话：xargs 把输出「变成参数列表」交给下一条命令，整批处理；-exec \; 是逐个处理。
致命坑：文件名带空格时 xargs 会切错。my note.txt 会被当成两个参数 my 和 note.txt。解法是两头都加 -0：find . -print0 | xargs -0 rm——用 \0 当分隔符，空格就安全了。删文件的场景，务必加 -0。

三个实战配方（直接抄进实操记录）

# 配方 1：这个项目里提到 TODO 的 Python 文件，按修改时间排
grep -rn --include="*.py" "TODO" . | cut -d: -f1 | sort -u | xargs ls -lt 2>/dev/null | head -n 5

# 配方 2：当前目录下大于 50MB 的文件，按大小排（没有输出 = 没有这么大的文件）
find . -type f -size +50M -exec ls -l {} + | sort -k5 -n | tail -n 5

# 配方 3：日志里出现最多的前 5 个 URL
awk '{print $4}' ~/linux-lab/logs/access.log | sort | uniq -c | sort -rn | head -n 5
配方 3 里的 $4 是按今天这份练习日志的列位置写的（字段依次是日期 / 时间 / 方法 / URL / 状态 / 字节）。真实 nginx 日志第 1 列是客户端 IP，所以「找访问最多的 IP」只要把 $4 换成 $1——D020 的 logtool 里那段 Top IP 统计就是这个意思。拿别人的日志做统计前，先 head -n 1 看一眼列的顺序，别硬套字段号。
把配方 3 的路径换成 /var/log/system.log 试一下，多半会报 Permission denied——系统日志普通用户读不了。为什么读不了、怎么才能读，是 D023 的主题。今天先在 ~/linux-lab/logs/access.log 上把逻辑跑通，明天讲完权限再回来看真日志。
这三条配方覆盖了 90% 的「找东西」需求：按内容找文件、按大小找文件、按频次统计。记不住参数没关系，记这三条的形状就够了——管道串起来的意义就是「每一步只干一件小事，把结果交给下一步」，这也是 shell 和 Python 最像的地方。

5通配符与引号：为什么 rm 会删过头

这一节比前面五节加起来都重要。路径写错只是找不到，引号写错是真会删错东西。

通配符是 shell 先展开的，不是命令自己认的

cd ~/linux-lab/logs
echo *.log
echo "*.log"
echo '*.log'
access.log old.log
*.log
*.log
看第一行：echo *.log 打出来的不是 *.log，而是目录里的文件名。因为 shell 在把参数交给 echo 之前，就已经把 *.log 展开成了实际匹配的文件。这就是「glob 展开」——命令本身根本没见过星号。
加引号就阻止了展开："*.log" 和 '*.log' 都是原样传过去。所以 find . -name "*.py" 的引号是必须的——不加的话，shell 会在当前目录展开成 main.py helper.py，find 只会去查这两个名字，别处的全漏了。

三种引号，记住这三行就够

写法$变量 展开吗通配符展开吗用在哪
"双引号"展开不展开默认就用这个
'单引号'不展开不展开要写含 $ 的字面量，如 awk 脚本
不加引号展开展开只在确定要匹配文件时用
cd ~/linux-lab
name=access
echo "logs/$name.log"
echo 'logs/$name.log'
awk '{print $4}' logs/access.log | head -n 1
logs/access.log
logs/$name.log
/index.html
最后一行是重点：awk 的 {print $4} 必须用单引号。用双引号的话，shell 会先把 $4 当成「脚本的第 4 个参数」展开成空，awk 收到的是 {print }，什么都不打印、也不报错。「不报错但结果不对」是 shell 里最常见的失败方式。

文件名带空格：一个永远不会自己消失的坑

cd ~/linux-lab
touch "my note.txt"
ls
find . -name "my note.txt"
find . -name "*.txt" | xargs wc -l
docs		logs		my note.txt	src
./my note.txt
wc: ./my: open: No such file or directory
wc: note.txt: open: No such file or directory
1 ./docs/readme.txt
1 total

换成用空字符分隔，就完全正常了：

find . -name "*.txt" -print0 | xargs -0 wc -l
1 ./docs/readme.txt
0 ./my note.txt
1 total
对比这两行输出，问题一清二楚：不带 -0 时，./my note.txt 被切成了两个参数，wc 找不到叫 ./my 的文件。带 -print0 / -0 用空字符分隔，空格就不再是问题。
规则：脚本里遍历文件，一律用 find ... -print0 | xargs -0 或者 find ... -exec ... {} +，不要用裸管道。手动敲命令时可以偷懒，写成脚本就必须严谨——脚本是要重复跑的，一次踩上就天天踩。
zsh 的额外差异（今天就撞得到）：在你的 Mac 上敲 ls *.py 而当前目录没有 py 文件时，zsh 会直接报 zsh: no matches found: *.py 并不执行命令；而 bash 会把字面量 *.py 传给 ls，由 ls 报 No such file or directory。同一个错误，两套报错文字——搜报错时两种都搜一下。

6BSD 与 GNU：同一件事，两种写法

今天最实际的一节。你搜到的每条 Linux 命令，在 Mac 上大概有 5% 会报错——因为 macOS 用的是 BSD 版本的这些工具，不是 GNU 版本。参数长得像，行为不一样。

如果你在 Windows 的 Git Bash 里对照，它属于「GNU」那一列。实测那台机器上是 sed 4.9、ls 8.32，date -d、sed -i 都能直接用——表里「报错长什么样」那列对它一律不成立。这也是为什么第 1 节说两边的血统是反的：同一张表，Mac 看右两列，Windows 看左两列。
先纠一处我自己写错的地方：这张表第一行对你这台 Mac 不成立。2026-11 实测确认，ls --color=auto 在 macOS 26 上不报错、还真的上了色——苹果把 FreeBSD 上游的改动并了进来，系统 ls 已经认 --color=when。可 macOS 14 及更早仍然报 ls: illegal option -- -。同一个参数，两台 Mac 上结论相反，网上教程谁说的都对——在他那台上。
所以「报错长什么样」那一列要这样读：它描述的是旧版 macOS，不一定是你手上这台。

三十秒查清你手上这个命令是哪一版

这是今天真正该带走的能力。不是背哪条会报错，而是任何一条从网上抄来的命令，你能在三秒内判断它在这台机器上行不行。

第 3 步是关键：033 就是 ESC，颜色靠它和后面的 [0;34m 这类控制序列实现，不是终端自己给文件名染的色。看到 033 说明真的输出了颜色码；只看到文件名、没有 033，说明这个参数被接受了但没生效。

颜色怎么关掉

cd ~/linux-lab
ls --color=never         # 只要这一次不要颜色
\ls                       # 绕过别名，直接调原始的 ls
echo $CLICOLOR           # 空 = 没开；有值说明环境变量在给 ls 上色
docs	logs	my note.txt	src
docs	logs	my note.txt	src
（第三行是空的：echo $CLICOLOR 什么都没打印，说明这个变量没设）
颜色不会「残留」到下一条命令。--color=auto 是这一次调用的参数，不是全局设置，敲完就没了——下一条 ls 有没有颜色，只看那一条自己怎么被调用。
但如果你发现「一直都有颜色」，那不是残留，是别名。很多教程和 oh-my-zsh 会在 ~/.zshrc 里写 alias ls='ls -G' 或 export CLICOLOR=1，于是每条 ls 都自带颜色。查一下 type ls 和 echo $CLICOLOR 就清楚了，改也只需要改那一行。
反过来有一条硬规则：--color=always 绝不能进管道。实测（GNU ls 8.32）：
ls --color=always | grep -c '^a.txt'   # 期望 1，实际 0
ls --color=never  | grep -c '^a.txt'   # 期望 1，实际 1
0
1

原因：每个文件名前面都被塞了 033[0m033[00;31m 这样的前缀，所以行首不再是 a，^ 锚点直接失配。更坑的是 --color=always 让字节数从 9 涨到 37，你 wc -c 出来的大小也不对了。所以 auto 不是「随便选的默认值」，它是唯一安全的选择：终端里给你看颜色，管道里自动变干净。

为什么值得多花这三十秒：「参数认不认」和「功能生不生效」是两件事，中间隔着一层。--color=auto 里的 auto 就是那层的开关——输出到终端才上色，输出到管道或文件就自动关掉。这也是为什么 ls | grep 永远不会被颜色码污染，而 ls --color=always | grep 会（见下面那条）。

这张表要拆成两半看：会松动的，和不会松动的

你这台机器上已经有两条不成立了，都是实测出来的：ls --color=auto（rc=0，上了色）、readlink -f docs（rc=0，输出 /Users/loogn/linux-lab/docs）。原因同一个：苹果从 macOS 26 起把 FreeBSD 上游的改动并了进来，而 FreeBSD 这些年一直在往 GNU 的长选项靠。

类别表里哪些会不会松动
长选项支持ls --color、readlink -f会，而且已经在松。BSD 系为了兼容 Linux 脚本，陆续补上 GNU 风格的长参数。今天能用不代表明年还能用——反过来说，今天报错也不代表明年还报错
语义与设计sed -i 要备份后缀、date -d vs -j -f、stat -c vs -f、grep -P、find -printf、cat -A不会。这些不是「还没实现」，是两边各自选择了不同的做法。比如 BSD 的 sed -i 强制给备份后缀，是它的设计意图；date -j -f 是另一种解析思路。没有谁要向谁让步
整套生态systemctl、apt、free不会。这不是参数差异，是换了操作系统：macOS 没有 systemd、没有 apt、内存管理方式也不同
所以你判断一条命令能不能用，先问它属于哪一类：是长选项（查一下、试一下就知道）、还是语义（一定要改写法）、还是整套生态（根本别找，直接换 Mac 的做法）。第一类会随时间变，后两类不会——这就是为什么「背结论」的价值有限，「当场试」的价值很高。

怎么判断「我这台报的这个错是不是 BSD 的锅」

  1. 看报错里有没有 illegal option 或 unknown primary。有 = 参数不被支持，八成是 BSD 与 GNU 的差异。
  2. 看搜索结果里的命令有没有长参数（--help 那种双横线）。BSD 工具大多只认单字母短参数，--long-option 基本都会报 illegal option。但这道界线在松动——macOS 26 的 ls 认了 --color、readlink 认了 -f，所以「报错」永远是最终判据，「应该会报错」不是。判断方法：拿一个真实存在的文件当靶子，加 ; echo "rc=$?" 一起跑。靶子不存在时，你分不清「参数不支持」和「文件不存在」——今天的 readlink -f f 就是这么静默的。
  3. 两边都要用就装 GNU 版：brew install coreutils gnu-sed grep findutils，装完这些命令带 g 前缀（gls gsed ggrep gfind）。今天不用装，等 D024 写脚本真需要了再说。
想亲手看 GNU 的行为？你的 Mac 上有 OrbStack，起一个 Linux 容器就有完整的 GNU 环境：docker run --rm -it alpine sh（在 OrbStack 里跑，镜像很小）。同一条命令两边各敲一次，差异就记住了——比背这张表有效得多。这一步可选，不装也没关系。

第 1 题 · 建一个三层目录，一次命令完成

在 ~/linux-lab 下建 archive/2026/11 三层，且如果 archive 已存在不要报错。

答案

第 2 题 · 找出所有 .py 文件，统计总行数

答案

# 只要总数：

 1 ./src/main.py

tail -n 1 取最后一行（total）。文件名可能带空格时要把管道换成 -print0 | xargs -0。

第 3 题 · 日志里 4xx 和 5xx 各有多少条

答案 
cd ~/linux-lab
grep -cE " (4|5)[0-9][0-9] " logs/access.log
# 分开数：
grep -cE " 4[0-9][0-9] " logs/access.log
grep -cE " 5[0-9][0-9] " logs/access.log
2
1
1

要点是状态码两边要有空格：只写 4[0-9][0-9] 会把 URL 里的数字（如 /api/v4）和字节数（如 1024）也算进去。正则写得越松，假阳性越多——D015 的教训在这里同样适用。

第 4 题 · 找出访问次数最多的 URL（前 3 个）

答案 
cd ~/linux-lab
awk '{print $4}' logs/access.log | sort | uniq -c | sort -rn | head -n 3
   2 /index.html
   1 /api/users
   1 /api/login

四步管道：取列 → 排序 → 计数去重 → 按次数倒序 → 取前 3。中间的 sort 不能省，因为 uniq 只合并相邻重复行。

第 5 题 · 把 access.log 里所有 500 的行单独存成一个文件

答案 
cd ~/linux-lab
grep " 500 " logs/access.log > logs/errors.log
cat logs/errors.log

2026-11-20 10:02:30 GET /api/users 500 64

grep -rni "note" docs/

第 7 题 · 找出当前目录下占用空间最大的 3 个目录

答案 
cd ~/linux-lab
du -sh */ | sort -h | tail -n 3
4.0K	docs/
8.0K	logs/
8.0K	src/

三个目录都在，都只有几 K——因为每个里面只放了一两个文件，而 du 按 4K 块向上取整，readme.txt 只有 9 个字节也报 4.0K（数字随文件系统变，见第 3 节那段说明）；logs 和 src 同为 8.0K 时先后顺序不固定。du -sh */ 只统计一级子目录、不展开；sort -h 按「人类可读大小」排（1K < 2M < 3G，普通 sort 会把 10K 排在 2M 后面）。如果 sort -h 在你的系统上报错，说明 BSD sort 版本老，改用 du -sk */ | sort -n | tail -n 3（-k 单位统一为 KB，-n 按数字排）。

第 8 题 · 一条命令：找出所有 .log 文件里含 "500" 的文件名（不输出内容）

答案 
cd ~/linux-lab
grep -rl "500" --include="*.log" .
./logs/access.log
./logs/old.log

-l（小写 L）只输出文件名。出现两个是因为「第二组」里用 cp + mv 复制过一份 old.log——它内容一样，自然也命中。这正好是那句老话的现场版：练习目录里留下的副本，会到处污染你的统计结果。
用法上很实用：先 -l 定位是哪几个文件，再对单个文件 grep -n 看具体行，比一上来就递归全文搜索好读得多。
