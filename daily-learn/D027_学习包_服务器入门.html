0先决定路线：零成本也能走完全流程

今天要练的六件事：连上 Linux、传文件、装软件、配 nginx、开端口、验证访问。其中只有「公网 IP」这一项必须花钱，其余全都能在本地完成。所以你有两条路，先选一条再动手。

路线 A · 本地容器（零成本）路线 B · 云服务器
需要什么你的 Mac + OrbStack（已装）一台云主机 + 一点预算
能得到什么localhost:8080 和局域网 IP 能访问公网 IP / 域名能访问
练不到的ssh 登录、systemd 服务管理、安全组—
适合先把 nginx 和页面跑通真的要给别人一个链接
建议：目标先定成「局域网能访问」。原因很实际——你今天要学的是 nginx 和文件权限，不是买机器。容器路线能把这两件事完整练一遍，而且失败了删掉重来零成本。等页面在局域网能打开、你自己觉得拿得出手了，再花钱买公网 IP 那一层。
关于价格，我不给具体数字。云厂商的学生优惠、新用户首年价、活动价每年都在变，我报了也是过时的。你需要自己去官网看「轻量应用服务器」的最低配——今天这套 nginx 静态站，最低配完全够，不需要高配。真要买，按年买比按月划算，但先按月试一个月，确认自己会持续用再续。

路线 A：用 OrbStack 起一个带 nginx 的 Linux

OrbStack 能跑 Docker。下面这条命令起一个 nginx 容器，把容器里的 80 端口映射到你 Mac 的 8080，再把你的本地目录挂进去当网站根目录。

mkdir -p ~/site
cat > ~/site/index.html <<'EOF'
<!DOCTYPE html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>我的第一台服务器</title></head>
<body>
  <h1>上线成功</h1>
  <p>这个页面由 nginx 提供，文件放在 Mac 上。</p>
</body>
</html>
EOF

docker run -d --name web -p 8080:80 \
  -v ~/site:/usr/share/nginx/html:ro \
  nginx:alpine

curl -I http://localhost:8080
HTTP/1.1 200 OK
Server: nginx/1.27.x
Content-Type: text/html
Content-Length: 186
Last-Modified: ...
Connection: keep-alive
ETag: "..."
Accept-Ranges: bytes
-p 8080:80 的读法是「宿主机端口 : 容器端口」。左边是你访问的、右边是 nginx 听的。为什么不用 80 直接映射：Mac 上 80 端口常被系统或其他软件占着，而且小于 1024 的端口需要 root 权限。用 8080 起步，稳定了再考虑 80。
-v ~/site:/usr/share/nginx/html:ro 是把本地目录挂进去，:ro 表示容器只能读——这样容器出问题也改不了你的文件。改完 ~/site/index.html，刷新浏览器就生效，不用重启容器。
# 看 Mac 的局域网 IP（Wi-Fi 一般是 en0）
ipconfig getifaddr en0

# 手机/平板连同一个 Wi-Fi，浏览器打开 http://刚才那个IP:8080
手机能打开，今天就算完成一半。因为它证明了完整链路：文件在磁盘上 → 通过挂载进了容器 → nginx 读到它 → 端口映射出来 → 局域网可达。换成云服务器，这条链只差「最后一跳是公网」。后面所有排错，都是在这条链上找断点。
容器路线的三个限制，先知道，别到时候以为是自己配错了：
① 没有 systemd：systemctl 在容器里不工作，起停服务要用 nginx -s reload 或者直接重启容器；
② 没有 ssh：容器里没有 sshd，进容器用 docker exec -it web sh；
③ 进程一退容器就停：nginx 是容器的主进程，它挂了容器就结束了，用 docker logs web 看原因。
想练 ssh 和 systemctl，用云服务器，或者 OrbStack 里的「Linux 虚拟机」功能（不是容器，有完整 init 系统）。

1路线 B：买机器与开安全组

买之前先搞清楚一件事：云服务器默认是「什么端口都不通」的。不是机器没开，是云厂商在安全组 / 防火墙那一层把流量挡了。这是「我明明按教程配好了，为什么打不开」的第一大原因。

买入时只改三件事

  1. 镜像选 Ubuntu LTS（不要选 CentOS 老版本、不要选带面板的镜像）。LTS 的意思是长期支持，文档最多、教程最多。
  2. Login 方式选「SSH 密钥」，如果只能选密码，就选一个强密码，登进去第一件事改掉（第 2 节）。
  3. 不要勾「自动创建快照/备份」之外的花钱项，尤其带宽——按流量计费在被人扫到时会悄悄烧钱，选固定带宽。

安全组要开三个端口

端口协议给谁不开会怎样
22TCP只给你的 IP（能限定就限定）连不上，ssh 超时
80TCP所有人 0.0.0.0/0网页打不开
443TCP所有人HTTPS 打不开（今天可选）
不要把 22 端口开给 0.0.0.0/0 然后继续用密码登录。公网 IP 上的 22 端口几分钟内就会被扫到，然后是一整天的暴力破解。两件事必须做其一：① 安全组里 22 只放你当前的出口 IP；② 关掉密码登录，只认密钥（下一节）。两个都做最稳。
顺带：3306（MySQL）、6379（Redis）永远不要开到公网。D029 之后你会用到这两个端口，它们只能在服务器内部或 ssh 隧道里访问。

2首次登录：十分钟内把安全底子打好

# ① 用 root 登进去（云厂商给你的默认用户可能是 root 或 ubuntu）
ssh root@你的公网IP

# ② 看看系统版本和时间
lsb_release -a
date
timedatectl | head -n 5
# ③ 建一个自己的普通用户，并给 sudo 权限
adduser loogn
usermod -aG sudo loogn

# ④ 把自己的公钥装给这个用户（在本地 Mac 上执行）
ssh-copy-id loogn@你的公网IP

# ⑤ 用新用户登录，确认能 sudo
ssh loogn@你的公网IP
sudo whoami
root
sudo whoami 输出 root，说明 sudo 权限生效了。这是验证权限最省事的一条命令——比去看 /etc/sudoers 快一百倍。
为什么一定要建普通用户、不用 root 日常操作：root 敲错一条 rm -rf 就是系统级的；普通用户加 sudo，至少每个危险操作都要再输一次密码，那两秒就是你的最后一道防线。

关掉密码登录，只认密钥

sudo vim /etc/ssh/sshd_config
# 找到并改成（前面的 # 要去掉）
PubkeyAuthentication yes
PasswordAuthentication no
PermitRootLogin no

# 顺手改端口（可选，能减少一大半扫描噪音）
Port 2222
改 sshd_config 有个著名的事故：改完 reload，然后自己再也连不上，只能去云控制台用 VNC 救援。
三个保命动作，一个都不能省：
① 改之前先备份：sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak；
② 改完先检查语法：sudo sshd -t，没输出才是对的；
③ reload 之后，另开一个终端试登录，确认新连接能进，再关掉旧的那个。永远不要在当前会话里 reload 完就退出——那等于把门锁上再确认钥匙对不对。
另外改了 Port 2222 就必须同步改安全组，否则新端口不通。
sudo sshd -t                    # 检查语法，无输出才是对的
sudo systemctl reload ssh       # Ubuntu 上服务名是 ssh，不是 sshd
# 另开终端确认：
ssh -p 2222 loogn@你的公网IP
reload 和 restart 的区别，在服务器上很重要：reload 让服务重新读配置但不断已有连接；restart 是停掉再起，所有连接瞬断。改 nginx 配置、改 sshd 配置都用 reload；只有升级了软件版本才需要 restart。你要是对 sshd 用 restart，等于自己把脚下的地板抽掉。

3把页面传上去

D023 的组合 5 今天直接用上。传文件有两个层次：偶尔传一次用 scp，反复同步用 rsync。

# 先在服务器上建好目录（用你自己的用户，不要 root）
ssh myserver "mkdir -p ~/site"

# 传单个文件
scp ~/site/index.html myserver:~/site/

# 传整个目录
scp -r ~/site/. myserver:~/site/

# 反复同步用 rsync（只传改动过的）
rsync -avz --delete ~/site/ myserver:~/site/
rsync --delete 会删掉目标目录里「源目录没有的文件」。这是它的价值（保证两边一致），也是它的风险（路径少写一个 /，可能删错地方）。
源路径末尾的斜杠很关键：~/site/ 是「site 里的内容」，~/site 是「site 这个目录本身」。写 rsync -avz --delete ~/site myserver:~/ 的后果和你想的可能不一样。第一次用先不加 --delete，跑通了再加。
为什么传到自己家目录 ~/site 而不是直接传到 /var/www/html：因为 /var/www 属主是 root，scp 没有权限写。标准做法是「传到有权限的地方，再用 sudo 搬过去」——下一步就这么做。另一种做法是改 /var/www 的属主给你自己，省掉每次 sudo，但安全性差一点（D023 第 1 节讲过 chown）。先用 sudo 搬，稳。

4装 nginx，托管你的页面

sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx
systemctl status nginx | head -n 5
● nginx.service - A high performance web server and a reverse proxy server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
     Active: active (running) since ...
       Docs: man:nginx(8)
enable --now 是两个动作合一：enable 让它开机自启，--now 顺手现在启动。只 start 不 enable，重启服务器之后网站就没了——这是「昨天还好好的，今天打不开」的经典原因。Linux 上没有 macOS 的 brew services，用的是 systemctl。

看懂 nginx 的目录结构

/etc/nginx/ ├── nginx.conf ← 主配置，一般不用改 ├── sites-available/ ← 「可用的站点」定义都放这 │ └── default ├── sites-enabled/ ← 启用的站点（是上面的软链接） │ └── default → ../sites-available/default ├── conf.d/ ← 另一种放法，效果一样 └── snippets/ /var/www/html/ ← 默认网站根目录（你的文件放这） /var/log/nginx/ ├── access.log ← 访问日志 └── error.log ← 错误日志（排错看这个）
# 看看默认站点怎么配的
cat /etc/nginx/sites-available/default
server {
    listen 80 default_server;
    listen [::]:80 default_server;

    root /var/www/html;
    index index.html index.htm;

    server_name _;

    location / {
        try_files $uri $uri/ =404;
    }
}
这五行是全部要害：listen 80 听哪个端口、root 网站文件在哪、index 默认打开哪个文件、server_name 匹配哪个域名（_ 表示「兜底，谁访问都行」）、try_files 先找文件再找目录，都没有就 404。
要做的事只有一件：把文件放进 /var/www/html/。配置一行都不用改。
# 搬文件 + 设属主 + 设权限（三步都要）
sudo cp -r ~/site/. /var/www/html/
sudo chown -R www-data:www-data /var/www/html
sudo chmod -R 755 /var/www/html

# 检查配置语法，然后 reload
sudo nginx -t
sudo systemctl reload nginx

# 在本机验证
curl -I http://localhost
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Date: ...
Content-Type: text/html
Content-Length: 186
Last-Modified: ...
Connection: keep-alive
ETag: "..."
Accept-Ranges: bytes
为什么必须 chown www-data：nginx 的工作进程以 www-data 用户运行，不是 root。文件属主是 root 且权限 644 时，nginx 能读（其他人有 r）；但如果你把权限写成 600，nginx 就读不了，返回 403。
403 Forbidden 在 nginx 里 90% 是这两个原因：① 文件权限里「其他人」没有 r；② index.html 根本不在那个目录。看到 403 先 ls -l /var/www/html，不要先改配置。
sudo nginx -t 这一步不能省。配置写错时 reload 会失败，而失败的表现是「网站还开着，但用的是旧配置」——你会以为改动没生效，其实是根本没加载。nginx -t 会明确指出哪一行错了，包括行号。

加一个自己的站点（不改 default）

sudo vim /etc/nginx/sites-available/mysite
server {
    listen 80;
    server_name mysite.local;      # 有域名就写域名，没有就写 _

    root /var/www/mysite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    # 给静态资源加缓存（可选）
    location ~* \.(css|js|png|jpg|svg)$ {
        expires 7d;
    }
}
sudo mkdir -p /var/www/mysite
sudo cp ~/site/index.html /var/www/mysite/
sudo chown -R www-data:www-data /var/www/mysite

# 启用：在 sites-enabled 里建软链接（这就是「启用」的全部含义）
sudo ln -s /etc/nginx/sites-available/mysite /etc/nginx/sites-enabled/

sudo nginx -t && sudo systemctl reload nginx
sites-available 和 sites-enabled 的分工，就是 D023 讲过的软链接：配置写在 available 里，启不启用看 enabled 里有没有那个链接。「停用一个站点」= 删掉 enabled 里的软链接（sudo rm /etc/nginx/sites-enabled/mysite），配置本身还在，随时能再启用。这比注释掉配置块干净得多。

5打不开的时候，按这个顺序查

「网页打不开」有五个不同的断点，从外往内一层层查，不要跳。跳过任何一层，你都会在错误的地方浪费半小时。

① 网络通不通 ping / 安全组 ② 端口通不通 nc -vz IP 80（本机没有 nc 就用 curl -v） ③ nginx 在不在跑 systemctl status nginx ④ nginx 有没有报错 tail /var/log/nginx/error.log ⑤ 文件在不在、权限对不对 ls -l /var/www/html
# ① 网络
ping -c 3 你的公网IP

# ② 端口（在本地 Mac 上跑）
nc -vz 你的公网IP 80

# ③ 服务
systemctl is-active nginx

# ④ 日志（在服务器上跑，-f 可以实时看）
sudo tail -n 30 /var/log/nginx/error.log

# ⑤ 文件
ls -l /var/www/html
curl -I http://127.0.0.1
现象断点动作
浏览器转圈到超时① 或 ②安全组没开 80；或者服务没起
连接被拒绝（Connection refused）③nginx 没跑，systemctl status nginx 看原因
403 Forbidden⑤权限里没有 r，或 index.html 不在
404 Not Found⑤路径对不上：root 指的目录里没有这个文件
502 Bad Gateway—nginx 在，但后面的程序挂了（今天没有后端，不会遇到）
还是旧页面—浏览器缓存；或者 reload 失败用了旧配置
最有用的一条：先在服务器上 curl -I http://127.0.0.1。如果本机能拿到 200，说明 nginx 和文件都没问题，问题百分之百在外面（安全组、端口映射、DNS）；如果本机都不行，就别在外层浪费时间。这一步把「五个断点」一刀切成两半。
容器路线遇到 403，多半是挂载的目录权限问题。容器里的 nginx 以 nginx 用户（UID 101）运行，而你 Mac 上的文件是 UID 501。目录权限是 700 时，容器读不进去。解法：给目录加「其他人可读执行」，chmod -R a+rX ~/site（X 大写 = 只给目录加 x，不给文件加）。

6域名与 HTTPS（可选，但值得知道）

如果只是自己练，公网 IP 直接访问就够了，这一节可以跳过。但如果你要把链接发给别人，一个 IP 加一个 http 的网址，说服力远不如一个域名加 HTTPS。

域名：一条 A 记录的事

  1. 买一个域名（便宜的几块到几十块一年，价格各平台浮动，自己比）。
  2. 在域名的 DNS 里加一条 A 记录：@ 或 www 指向你的公网 IP。
  3. 等生效（几分钟到几小时），用 dig 你的域名 +short 确认解析到了那个 IP。
  4. 国内服务器的域名需要备案，这一步比技术麻烦得多——没有备案的国内服务器，80 端口用域名访问会被拦。
「国内服务器必须备案」这一条是硬规定，不是建议。如果你不想折腾备案，两条路：① 用 IP 访问（个人练习完全够）；② 用境外服务器（速度慢，且要注意合规）。先别碰备案，你现在的目标是把 nginx 跑通。

HTTPS：certbot 一条命令

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d 你的域名

# 它会自动改 nginx 配置、申请证书、设好自动续期
sudo certbot renew --dry-run
certbot --nginx 会自动帮你做三件事：申请证书、写进 nginx 配置、加一条「http 跳 https」的重写规则。证书 90 天到期，certbot 装的时候已经加了自动续期的定时任务，用 --dry-run 验证续期流程能不能跑通——这一步别省，不然三个月后证书过期、网站报警，你早忘了当时怎么配的。

7部署自检脚本：把上面所有检查写成一条命令

D024 第 7 题那个 check() 函数，今天正好用。部署完跑一次，比手点五遍可靠。

cat > ~/deploy-check.sh <<'EOF'
#!/bin/bash
set -uo pipefail      # 不加 -e：要跑完所有检查再汇总

HOST="${1:-127.0.0.1}"
fail=0

check() {
  local name="$1"; shift
  if "$@" >/dev/null 2>&1; then
    printf '  OK    %s\n' "$name"
  else
    printf '  FAIL  %s\n' "$name"; fail=1
  fi
}

echo "检查目标：$HOST"
check "nginx 服务在跑"      systemctl is-active --quiet nginx
check "配置语法正确"        nginx -t
check "80 端口在监听"       bash -c "ss -lnt | grep -q ':80 '"
check "站点根目录存在"      test -d /var/www/html
check "首页文件存在"        test -f /var/www/html/index.html
check "首页可被 www-data 读" sudo -u www-data test -r /var/www/html/index.html
check "本机 HTTP 返回 200"  bash -c "curl -fsS -o /dev/null http://127.0.0.1"
check "错误日志近 10 行无 error" bash -c "! sudo tail -n 10 /var/log/nginx/error.log | grep -qi '\[error\]'"

if [[ $fail -eq 0 ]]; then
  echo "全部通过"
else
  echo "有检查未通过，按第 5 节的顺序往下查"
  exit 1
fi
EOF
chmod 755 ~/deploy-check.sh
~/deploy-check.sh
检查目标：127.0.0.1
  OK    nginx 服务在跑
  OK   配置语法正确
  OK    80 端口在监听
  OK    站点根目录存在
  OK    首页文件存在
  OK    首页可被 www-data 读
  OK    本机 HTTP 返回 200
  OK    错误日志近 10 行无 error
全部通过
这个脚本的价值不在「跑一次」，在「以后每次部署完都跑一次」。它会替你记住上次踩过的每一个坑：服务忘了 enable、权限忘了给 www-data、首页名字写成了 index.htm。把踩过的坑写成检查项，是不重复踩同一个坑的唯一有效办法。
脚本里用了 sudo -u www-data test -r，这是「以那个用户的身份试读」。它比看权限位更准——因为权限位只能告诉你 644，不能告诉你上级目录有没有 x 位。排查 403 时这一条最好用。注意脚本需要 sudo，所以要 sudo ~/deploy-check.sh 或者允许免密。

8练习八道

1–3 两条路线都能做，4–8 需要服务器（容器路线部分做不了，已标注）。

第 1 题 · 把页面换成一个带样式的版本，确认改动不用重启就生效

答案 
# 容器路线：直接改 Mac 上的文件（挂载是实时的）
vim ~/site/index.html
curl -s http://localhost:8080 | head -n 5

# 云服务器路线：改完要重新同步
vim ~/site/index.html
rsync -avz ~/site/ myserver:~/site/
ssh myserver "sudo cp -r ~/site/. /var/www/html/ && sudo chown -R www-data:www-data /var/www/html"
curl -s http://你的IP | head -n 5

差别在挂载和复制：容器是「同一个目录」，改了就变；服务器是「两份文件」，必须再传一次。
这就是为什么真实项目会用 CI/CD 或者 rsync 一键同步——手工 scp 十几次之后一定会漏一次，然后你会对着旧页面怀疑人生。

第 2 题 · 故意把首页改名，看错误码怎么变

答案 
sudo mv /var/www/html/index.html /var/www/html/index.html.bak
curl -I http://127.0.0.1
sudo mv /var/www/html/index.html.bak /var/www/html/index.html
HTTP/1.1 403 Forbidden

为什么是 403 不是 404：因为 try_files $uri $uri/ =404 里，$uri/ 匹配到了 目录本身，nginx 尝试列目录但没开 autoindex，于是拒绝。如果目录里连文件都没有，就会走 =404。
这个区别在排错时很有用：看到 403 说明路径是对的、文件不见了；看到 404 说明路径本身就不对。

第 3 题 · 让浏览器不缓存，看到最新文件

答案 
curl -I http://127.0.0.1/index.html
# 浏览器里：强制刷新 Cmd+Shift+R（Mac）

# 或者在 nginx 里对 html 关掉缓存
location ~* \.html$ {
    add_header Cache-Control "no-cache";
}

先分清是「服务器没更新」还是「浏览器缓存」：用 curl 直接取，看到的是服务器真实内容；curl 是新内容而浏览器是旧内容 = 纯缓存问题。这一步能把「我明明改了」的怀疑消掉一半。

第 4 题 · 用 systemd 查看 nginx 最近发生了什么

答案 
systemctl status nginx
journalctl -u nginx -n 30 --no-pager

# 只看今天的
journalctl -u nginx --since today --no-pager | tail -n 20

journalctl -u 服务名 是 systemd 的日志，记录「服务被启动、停止、失败」这类事件；/var/log/nginx/error.log 记录「请求处理出了什么问题」。两者是不同的东西——服务起不来查 journalctl，页面 403/404 查 error.log。

第 5 题 · 把它配置成开机自启，并验证「真的会自启」

答案 
sudo systemctl enable nginx
systemctl is-enabled nginx

# 验证：重启（谨慎，会断 ssh 几十秒）
sudo reboot
# 等 30 秒后重新 ssh 进去
systemctl is-active nginx
enabled
active

is-enabled 只说「配置里写了开机启动」，is-active 说「现在在跑」。两个都要是肯定答案。不过重启验证是最可靠的——很多「设置了但没生效」的情况，只有真重启才暴露。在云服务器上重启不会丢数据，但会中断几十秒，别在有用的时候做。

第 6 题 · 只允许你的 IP ssh，其他人连 22 都摸不到

答案 
# ① 先查自己的出口 IP（在本地 Mac 上）
curl -s https://api.ipify.org

# ② 云控制台 → 安全组 → 把 22 的源地址从 0.0.0.0/0 改成本地 IP/32
# ③ 验证：换手机热点（不同出口 IP）ssh 一下，应该连不上

/32 表示「只有这一个 IP」。安全组的规则是「允许」，所以要显式写来源。验证一定要换一个网络试——从同一个网络试，无论规则对不对都能连上，等于没验证。
副作用要知道：你的家庭宽带 IP 会变，某天突然连不上，先想到这一条。

第 7 题 · 加一个 404 页面

答案 
sudo vim /etc/nginx/sites-available/mysite
# 在 server 块里加：
#   error_page 404 /404.html;
#   location = /404.html { internal; }

sudo tee /var/www/mysite/404.html >/dev/null <<'EOF'
<!DOCTYPE html><html lang="zh-CN"><meta charset="utf-8">
<title>404</title><h1>这个页面不存在</h1><p><a href="/">回首页</a></p>
EOF
sudo chown www-data:www-data /var/www/mysite/404.html
sudo nginx -t && sudo systemctl reload nginx
curl -I http://127.0.0.1/nope
HTTP/1.1 404 Not Found
Server: nginx/1.24.0 (Ubuntu)
Content-Type: text/html

location = /404.html { internal; } 里的 = 是精确匹配，internal 表示「只能被 nginx 内部跳转，外部不能直接访问这个地址」。不加 internal 也能用，但别人可以手动打开 /404.html，看着很怪。

第 8 题 · 用一条命令把「部署 + 自检」连起来

答案 
cat > ~/deploy.sh <<'EOF'
#!/bin/bash
set -euo pipefail
HOST="${1:?用法: deploy.sh 服务器别名}"
SITE="${2:-$HOME/site}"

echo "== 同步文件 =="
rsync -avz --delete "$SITE/" "$HOST":~/site/

echo "== 上线 =="
ssh "$HOST" "sudo cp -r ~/site/. /var/www/html/ && \
             sudo chown -R www-data:www-data /var/www/html && \
             sudo nginx -t && sudo systemctl reload nginx"

echo "== 自检 =="
ssh "$HOST" "bash ~/deploy-check.sh"
EOF
chmod 755 ~/deploy.sh
~/deploy.sh myserver

这个脚本就三行有效内容，但它把「传文件、搬位置、改属主、查语法、重载、自检」六件事固定成了一条命令。以后每次改页面只要 ./deploy.sh myserver——手动步骤越少，漏步骤的可能越小。
注意它用 set -euo pipefail：任何一步失败就停，不会出现「文件没传上去但 nginx 已经 reload 了」这种半吊子状态。

八题里 2、4、5 是排错的基本功。真上线之后你会遇到的全部问题，几乎都能用「看错误码 → 看 error.log → 看服务状态」这三步定位。今天练的是流程，不是配置记忆。
